# Guardrails — 세 스킬(requirement-fanout·design-review·code-review)과 pipeline 오케스트레이터가 공유하는 운영 원칙

> **스택·트래커 무관**인 운영 원칙만 담는다. GitLab/mx.js/Asana처럼 특정 트래커에 결합된 규칙
> (메인 에이전트가 `total/`에서 `workspace/`로 옮기는 시점 등)은 다루지 않는다 — 그건 호스트
> 프로젝트의 몫이다. 이 문서는 순수 서술이라 Claude Code든 Codex든 동일하게 적용된다.

---

## 1. 역할 분리 — 분석·오케스트레이션 ≠ 구현

이 세 스킬과 `pipeline`은 **분석·검증·오케스트레이션 전용**이다. 프로덕션 코드를 직접 고치는 유일한
예외는 code-review의 auto_fix/Critical Loop(스코프가 diff 안으로 명시적으로 한정된 fix 패스)뿐이다.

- design-review가 dispatch하는 세 에이전트(devil-advocate/regression-analyst/runtime-trap)는
  **읽기 전용** — 설계 단계에서 코드를 고치는 검증자는 검증자가 아니라 두 번째 저자가 된다.
- code-review의 critic은 쓰기 도구를 갖지 않는다 — 판정만 하고, 판정을 근거로 남이(fix agent가)
  고친다.
- requirement-fanout의 persona-fanout/synthesizer는 스펙 문서만 쓴다 — 코드에는 손대지 않는다.

## 2. 부수효과 있는 명령 실행 전 상태 확인

리뷰·수정 패스가 Bash로 git 조작·파일 이동·스크립트 실행을 할 때:

- 실행 전 대상 상태를 먼저 확인한다 (`git status`/`ls`/`Read`로 경로·브랜치·존재 여부 확인 후 명령).
- 실패 시 같은 명령을 맹목적으로 재시도하지 않는다 — 실패 원인(경로/권한/상태)을 먼저 확인한 뒤
  1회 재실행한다.

근거: 사전확인 없이 실행→실패→재실행을 반복하면 도구 호출 실패율만 올라가고 실제 진행은 없다.

## 3. 리뷰 봇/패스는 게이트가 아니라 도구다

code-review의 5관점·critic·Critical Loop는 **결함을 없애는 수단**이지, 그 자체가 통과 기준이 아니다.

- **severity 라벨을 맹종하지 않는다** — 매 건 코드 근거로 실측 판정한다. 특히 자동화된 관점은
  파일 하나만 고립 분석해 cross-file 상태(락·트랜잭션 경계·상위 컨텍스트)를 못 보는 경우가 많다 —
  같은 지적이 반복 재발하면 봇 쪽 오탐일 가능성을 먼저 의심한다.
- **종결 조건은 Critical/실질 결함 0** — 그 이후 재진입은 (a) 방금 만든 fix가 유발한 회귀,
  (b) 신규 Critical(권한 우회·데이터 손실급) 둘 뿐이다. 그 외(경계 조임·nitpick·재발·오탐)는
  반증 근거를 남기고 accepted-risk로 명시한 뒤 멈춘다 — 봇이 0으로 수렴할 때까지 무한히 돈다고
  품질이 계속 오르지 않는다(비증분 전체 재리뷰는 매 fix마다 더 미세한 지적을 낳는다).
- **사람의 최종 승인(MR merge 등)은 이 절차가 대신하지 않는다** — 봇/리뷰 대응은 코드 품질 확보일
  뿐, 실제 병합·배포 승인은 호스트 프로젝트의 게이트(4)에 남는다.

## 4. 결함 클래스 단위로 방어·수정한다

벡터가 여럿인 "클래스" 문제(DoS·동시성·인젝션 등)를 한 경로씩 막으면, 다음 라운드에 같은 클래스의
다른 경로가 또 뜬다.

- **design-review 단계에서 클래스 전체를 한 번에 설계한다** — 벡터를 구현 후 리뷰 라운드마다
  하나씩 뽑게 두지 않는다(예: "업로드 DoS = 청크 거부 + 압축률 상한 + 총 해제량 상한 + 행/시트
  캡을 한 번에", "동시 등록 = 부모 행 비관적 락으로 트랜잭션 전체를 처음부터 직렬화").
- **code-review에서 결함 클래스를 고칠 때는 한 경로가 아니라 전 경로를 sweep한다** — 동일 패턴을
  grep으로 전수 수집한 뒤 공용 헬퍼로 일괄 교체한다. 한 곳만 고치면 다음 라운드에 같은 클래스의
  다른 위치가 다시 지적된다.

## 5. 검증 패스를 저자 패스보다 약하게 돌리지 않는다

**저자 ≠ 검증자는 컨텍스트만 분리하면 성립하는 게 아니다** — 검증 쪽 추론 강도가 더 낮으면 놓친
결함이 그대로 게이트를 통과한다.

> **비용 판단의 기준은 한 번의 실행이 아니라 총합이다.** 검증 강도를 낮춰 아끼는 토큰은
> 한 패스 분량이지만, 그렇게 놓친 결함 하나가 구현 뒤에 발견되면 재설계·재구현·재리뷰가 통째로
> 다시 돈다. **싸게 여러 번 도는 것보다 비싸게 한 번에 끝내는 쪽이 결국 덜 든다** — 애초에 이 킷이
> requirement-fanout → design-review → code-review 순으로 단계를 **앞으로 밀어놓은 이유와 같다.**
> 이 문서의 다른 원칙(§3 종결 조건, §4 클래스 단위 수정)도 전부 "같은 일을 반복하지 않는다"는
> 같은 계산에서 나온다.

모델/추론강도를 고를 수 있는 도구라면:

- **code-review 5관점은 최저 강도(haiku/low)로 절대 실행하지 않는다.** 결함 탐지가 목적인 적대적
  패스가 탐지력 낮은 강도로 돌면 "리뷰를 했다"는 기록만 남고 실제 방어력은 없다 — **거짓 안전감이
  가장 위험한 실패 모드다.** 보안·회귀 관점은 가용한 최고 강도를 권장한다.
- **design-review의 첫 패스(devil-advocate)도 낮추지 않는다.** 뒤따르는 regression-analyst·
  runtime-trap이 약한 전제를 이어받는 순차 구조라, 첫 패스의 약함이 그대로 전파된다.
- **critic도 낮추지 않는다.** `dropped` 판정은 반증 근거를 코드에서 직접 재확인해야 하는데,
  요약만 훑는 강도로는 그 확인이 부실해진다.

모델을 고를 수 없는 단일세션 CLI에서는 이 원칙을 **프롬프트로 대체한다** — 해당 패스에
"결론을 내기 전에 최소 3가지 반례를 스스로 찾아본 뒤 답하라"처럼 더 긴 사고를 명시적으로 요구한다.
강도를 못 올린다는 것이 이 스테이지를 건너뛸 이유는 아니다.

**진입점끼리 강도가 달라지면 안 된다.** 같은 방법론을 Claude Code로 돌릴 때와 Codex로 돌릴 때
탐지력이 다르면, 통과한 리뷰의 의미가 도구에 따라 달라진다 — 어느 쪽으로 돌렸는지가 기록에
남지 않으므로 나중에 구분할 방법도 없다. `.codex/config.toml`의
`default_subagent_reasoning_effort`는 Claude 쪽 에이전트 `model:` 설정과 **같은 급으로 맞춰둔다.**

## 6. 전역 설정 변경은 양방향으로 감사한다

공유 전역 설정(업로드 상한·보안 파서 옵션·마이그레이션 정책 등)을 바꿀 때는 "기존을 깨는가"뿐
아니라 "기존 방어를 약화시키는가"까지 감사한다. 전역 static 변경보다 해당 경로 로컬 방어를
우선한다 — 전역 변경은 다른 모든 경로에 조용히 영향을 주므로 최후수단이다.

## 이식 시 유지되는 것 / 갈아끼우는 것

| 항목 | 이식 시 |
|---|---|
| 1~2절(역할 분리, 사전확인) | 스택·프로젝트 무관 — 그대로 사용 |
| 3~4절(봇은 도구, 클래스 단위 방어) | 원칙은 그대로, 구체 예시(업로드 DoS 등)는 참고용 — 프로젝트 도메인에 맞는 예시로 대체해도 됨 |
| 5절(검증 강도 하한) | 원칙은 그대로 — 강도 표기(opus/high 등)는 도구·모델 라인업에 맞게 읽는다 |
| 6절(전역 설정 감사) | 원칙은 그대로 — "전역 설정"의 구체 목록은 프로젝트마다 다름 |
