## 시스템 개요

수집 대상 서버의 에이전트(상시 데몬, 10초마다 poll)가 주기가 되면 JSON 을 POST 하는 지점부터,
Caddy·`ingest.php`·MySQL·매처를 거쳐 웹 대시보드에 뜨기까지의 데이터 흐름이다. CVE 미러가
매처로 들어가 findings 를 만드는 갈래도 여기 있다. 에이전트가 보내는 것은 패키지·프로세스·노출만이
아니다 — 계정 인벤토리와 패키지 의존성 그래프(SBOM·pom), 호스트 IP·라우팅도 같은 경로로 들어와
MySQL 에 쌓인다.

**자산을 아는 길이 둘**이라는 것이 이 그림의 요점이다. 에이전트가 밀어 넣는 갈래 말고,
중앙이 등록된 대역을 직접 훑는 갈래(`bin/discover.php`)가 따로 있다 — 에이전트가 없는 자산을
찾는 것이 목적이라 접점이 IP 대조 한 곳뿐이다(자세히는 [자산 탐색](#자산-탐색)).

전체 그림에서 내가 건드리는 부분이 어디인지 먼저 잡을 때 본다.

## 매처 판정 로직

패키지에 영향을 주는 CVE 하나가 CRITICAL·HIGH·MEDIUM·LOW 중 무엇이 되는지, 아니면 억제되는지를
결정하는 분기다. 백포트 패치 근거(changelog·errata·debsecan)로 억제하되, 옛 `.so` 가 아직 물려 있거나
커널 재부팅 전이면 억제를 취소하는 갈래를 담았다. 억제되지 않고 남은 건은 런타임 상태 7종
(EXTERNAL·LAN·FILTERED·LISTENING·RUNNING·LOADED·INSTALLED)으로 기본 단계가 정해지고,
**KEV 등재는 그 위에 상태와 무관하게 한 단계를 더한다**(상한 CRITICAL) — 예전 그림은 KEV 가산을
외부노출 갈래에만 붙여 놓아 "설치만 된 KEV 는 LOW" 처럼 읽혔다. 실제 코드
(`server/src/matcher/classify.php` 의 `vg_classify`)는 모든 상태에 +1 한다.

"이 건은 왜 이 등급인가", "왜 억제됐는가" 를 따질 때 본다.

## 배포 구성

`compose_runner.sh` 의 dev(메인 트리 / 워크트리)·prod 실행이 각각 어떤 compose 레이어를 겹쳐 쓰는지,
Docker Secrets 가 어느 컨테이너로 들어가는지, prod 에서 caddy·web·scheduler·db 가 어떤 포트·내부망으로
붙는지를 보여준다. caddy 가 붙이는 보안 응답 헤더(CSP·nosniff·X-Frame-Options — HSTS 는 자체서명 확정이라
붙이지 않는다)도 그 노드에 적어 두었다.

에이전트 배포 경로도 같이 있다: web 컨테이너의 읽기전용 마운트 두 개(`../agent` 는 git 추적,
`../agent-ca` 는 배포마다 다른 루트 CA 라 gitignore)가 `agent-dl.php`(무인증·화이트리스트 4개)와
`agent-poll.php` 로 들어가고, 노드가 받은 파일을 어디서 검증하는지까지 표시했다. **서명 개인키는
이 서버에 오지 않는다** — 유지보수자가 커밋 전에 로컬에서 서명하므로 웹 티어가 침해돼도 악성
에이전트를 밀 수 없다. 검증 단계별 상세는 [에이전트 자동 업데이트](#에이전트-자동-업데이트)가 갖는다.

스택이 안 뜨거나, 어떤 compose 파일을 고쳐야 할지 헷갈릴 때 본다.

## ERD

`tb_host`→`tb_scan` 을 축으로 패키지·노출·프로세스·계정·의존성 그래프와 판정 결과, CVE 미러 쪽 테이블이
어떻게 엮이는지다(도메인 엔티티 59개 = 전체 60테이블 − `tb_schema_migrations`).
`tb_schema_migrations` 는 마이그레이션 러너 자신의 인프라 테이블이라 도메인 모델이 아니어서 **의도적으로**
뺐다 — `tests/documentation_consistency_test.php` 도 "ERD 엔티티 = DB 문서 표 − 마이그레이션 이력" 을
그대로 검사한다.
감사 4컬럼 중 `is_deleted` 만 표기했고, FK 없이 애플리케이션 조인으로만 엮이는 테이블은 소스에 주석으로 적혀 있다.
테이블명은 단수, 대리키 PK 는 `<단수 테이블명>_id`(`tb_host.host_id`)라 **조인 양쪽 이름이 같다**.
테이블별 전체 컬럼과 명명규칙 예외는 [`docs/dev/데이터베이스.md`](../../dev/데이터베이스.md) 가 따로 다룬다.

`tb_scan` 에 달린 **억제 근거 ②③④ 와 억제 취소 ⑤** 는 관계선이 몰려 있어 그림에선 번호만 적었다.
② `tb_pkg_changelog_cve` — changelog 에 그 CVE 수정 기록, ③ `tb_applied_errata` — 벤더 권고(errata),
④ `tb_debsecan` — 데비안 트래커(역방향), ⑤ `tb_stale_lib` — 패치는 됐는데 **옛 `.so` 가 아직 물려 있어
억제를 취소**하는 건(조치: 프로세스 재시작·재부팅). ⑤ 도 번호로 줄인 이유는 ④ 와 라벨이 같은 자리에
겹쳐 찍혔기 때문이다(PR #219 가 고쳤던 것과 같은 결함).

`tb_control_catalog`—`tb_control_mapping` 의 **"U-코드 커버리지"** 점선은 기반시설 가이드 72개 항목을
**분모**로, 우리가 실제로 매핑한 항목을 **분자**로 놓는 관계다(FK 없이 `framework`+`control_id` 자연키로
만난다). 매핑이 없는 항목 — 즉 우리가 안 덮는 항목 — 이 드러나는 것이 이 표의 목적이라 매핑 쪽에
FK 로 매달 수 없다.

**자산 탐색 4테이블은 별도 package** 로 묶었다. 취약점 스캔과 별개 파이프라인이라
`tb_discovered_asset.host_id` 하나로만 기존 자산과 만난다. 그 대조의 좌변인 `tb_host_address`(호스트가
가진 IPv4)와 세그먼트 맵의 원천 `tb_host_route`(직결 서브넷·기본 게이트웨이)는 에이전트 ingest 가 채우므로
수집 package 에 있다.

## 사이트맵

로그인부터 대시보드·호스트 상세·취약점·자산·피드·관리 화면까지의 구성이다. **화면마다 필요한 메뉴
권한을 `«assets»` 처럼 경로 옆에 적었다** — `server/src/view/nav.php` 의 `perm` 과 각 화면의
`vg_require_menu()` 값이 정본이고, 상세 화면처럼 여러 자리에서 열리는 것은 `vg_require_menu_any()` 를 써서
`«compliance 또는 findings»` 로 적었다. 에이전트 키 인증 API(`ingest.php`·`agent-poll.php`·
`agent-progress.php`), 세션 인증 내보내기(`export.php`·`sbom.php`)도 표시했다. 사람이 주소창에 치는 화면은
아니지만 화면이 뒤에서 부르는 엔드포인트(`agent-command-overview.php`·`agent-command-status.php`·
`feed_preview.php`)와 무인증 설치파일 배포(`agent-dl.php`)도 별도 묶음으로 두었다.

사이드바 항목 하나가 서브탭 여러 개를 여는 자리도 이동선으로 그렸다 — 자산 4탭(자산 목록 / 전체 설치 패키지 /
자산 탐색 / 세그먼트 맵), 컴플라이언스 3탭(컴플라이언스 매핑 / 기반시설 U-코드 / 통제 기준 매핑),
탐지 결과 5탭(취약점·보안설정·노출·변화·제거 권고).

`/index.php`(대시보드 자신)·`/logout.php`(리다이렉트)·`/language-packages.php`(옛 링크 호환용 302 shim,
실제 화면은 `/packages.php?tab=lang`)·`/styleguide.php`(업무 화면이 아닌 UI 디자인 시스템 참조 페이지,
어디에서도 링크되지 않는다)는 같은 화면을 두 번 그리게 되거나 업무 화면이 아니어서 넣지 않았다 —
이유는 소스 끝의 주석에 적어 두었다. 그 넷을 빼면 `server/public/*.php` 전부가 이 그림에 있다.

## 자산 탐색

에이전트를 설치한 서버만 알고 있으면 담당자가 목록에서 빠뜨린 자산을 구조적으로 못 찾는다. 그래서
관리 대역을 등록해 두면 중앙이 직접 훑는다 — 대역 등록(`tb_discovery_target`) → 스케줄러 틱이
pending 스캔 집행 → 2단계 TCP connect 스윕 → 역DNS·서비스 힌트·배너로 정체 채우기 →
`tb_host_address`(우리가 아는 IP)와 대조 → 안 맞으면 **에이전트 미설치 = 섀도우 IT 후보**.
왜 2단계인지(1단계 탐침 6포트로 살아있는 IP 만 추리고 2단계에서 그 IP 에만 전체 포트를 던진다),
왜 닫힌 포트를 저장하지 않는지도 그림에 적혀 있다.

취약점 스캔과는 **별개 파이프라인**이다(Nexpose·Nessus 의 Discovery Scan / Vulnerability Scan 분리와
같은 구도). 두 파이프라인이 만나는 곳은 IP 대조 한 곳뿐이다.

"이 IP 는 왜 미관리로 떴나", "탐색이 왜 아직 안 돌았나"를 따질 때 본다.

## 컴플라이언스 판정

이미 쌓여 있는 수집물(`tb_finding`·`tb_host`/`tb_scan`·`tb_cce_finding`·`tb_host_account`)이 통제 4종
(패치관리 / 정보자산 식별 / 보안시스템 운영 / 계정 관리)으로 집계되고, 판정 어휘 4종
(준수 / 판정 불가 / 부분준수 / 미준수)을 거쳐 하루 1건 `tb_compliance_snapshot` 에 증적으로 남기까지다.
**통제 4종은 판정을 새로 짜지 않는다** — CCE·계정 판정처럼 이미 있는 결과를 집계만 한다.
화면(`/compliance.php`)과 스케줄러가 같은 함수·같은 기준값(`tb_setting`)을 쓰는 것도 이 그림의 요점이다.
기준값을 한쪽만 쓰면 화면과 증적이 다른 답을 낸다.

"위반 0건인데 왜 준수가 아니라 **판정 불가**인가"가 이 그림에서 가장 자주 보게 될 자리다 — 근거를 못
걷어서 0건인 것을 준수로 표기하면 심사 증빙에 허위 안심을 싣게 되기 때문이다. 오른쪽 갈래는 같은
결과를 기준 언어로 바꿔 끼우는 길이고, `tb_control_catalog`(기반시설 U-코드 72개)를 분모로 놓아
덮지 못한 항목까지 드러내는 `/kisa-u.php` 가 거기 붙는다.

심사 자료를 만들거나 "이 통제는 무슨 근거로 이 상태인가" 를 따질 때 본다.

## 에이전트 자동 업데이트

에이전트가 10초마다 부르는 poll 에 자기 버전을 실어 보내고, 배포된 스크립트보다 낮으면 서버가
버전·sha256·서명을 응답에 실어 주는 데서 시작하는 시퀀스다. 노드가 무엇을 어떤 순서로 검증하고
(HTTPS 전용 → 다운그레이드 거부 → sha256 → Ed25519 서명 → `bash -n` → 백업 후 원자적 교체),
교체 뒤 **다음 실행의 자기점검**으로 적용을 확정하거나 롤백하는 갈래까지 담았다.

핵심은 sha256 과 서명의 **출처가 다르다**는 것이다. sha256 은 웹앱이 즉석 계산하므로 웹 티어가
침해되면 공격자가 준비한 파일의 해시가 그대로 "검증 통과" 가 된다. 서명은 유지보수자가 커밋 전에
로컬 개인키로 만들어 커밋에 실어 보내고 PHP 는 읽기만 하므로, 웹 티어만으로는 위조할 수 없다.
예외 갈래도 그려 두었다 — OpenSSL 3.0 미만 노드는 `pkeyutl -rawin` 이 없어 서명 검증을 건너뛰고
sha256 만으로 진행하되 조용히 넘어가지 않고 **명시적 저하로 서버에 보고**하고, HTTP 로 설치된 노드는
자동 업데이트 자체가 꺼진다.

새 에이전트를 배포하기 전이나, 특정 노드만 업데이트가 안 될 때 본다.
