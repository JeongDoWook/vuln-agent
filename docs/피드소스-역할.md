# 피드 소스(커넥터) — 각자 무슨 질문에 답하나

vuln-agent 는 서로 다른 성격의 취약점 정보원을 **역할별로** 조합한다.
하나의 소스로는 "이 취약점이 우리에게 얼마나 위험한가"를 답할 수 없기 때문이다.
각 커넥터는 아래의 서로 다른 질문에 답한다.

| 소스 | 답하는 질문 | 성격 | 우리 쓰임 |
|---|---|---|---|
| **NVD / OSV** | "이 취약점이 **무엇인가**" | 원본 정보 + 심각도(CVSS) + 영향 버전 | 취약점의 정체·설명·CVSS·영향 패키지의 기준 |
| **EPSS** | "**악용될 확률**이 얼마인가" | 예측(향후 30일 악용 확률 0~1) | 같은 등급 안에서 우선순위 정렬 |
| **CISA KEV** | "**실제로 악용되고 있는가**" | 확정된 사실(실측 악용 목록) | 등급 상향의 결정타 — 외부노출 + KEV = CRITICAL |
| **KISA** | "**한국 맥락**에서 챙길 게 있나" | 지역 보완(보호나라 국내 보안공지) | 해외 스캐너가 다루지 않는 국내 특화 정보 |
| **데비안 보안 트래커** | "이 데비안 빌드가 **아직도 취약한가**" · "**고칠 수는 있나**" | 배포판 벤더의 판정 | **백포트 오탐 제거** + 수정본이 아직 안 나온 건 `조치 불가` 로 분리 |
| **RHEL 계열 벤더 권고(OVAL)** | "이 CVE 는 **어느 EVR 에서 고쳐졌나**" | 배포판 벤더의 판정 | RHEL·Alma·**Oracle** 의 백포트 판정 + **취약 후보의 유일한 소스**(OSV 엔 이 배포판 데이터가 없다) |
| **Red Hat 미수정 CVE** | "벤더가 **고칠 생각이 있는가**" | 벤더의 조치 상태 | OVAL 엔 수정본만 있다 → **패치가 없는 취약점**을 "조치 불가" 로 표시 |
| **우분투 보안 OVAL** | "우분투가 **고쳤나 / 고칠 수는 있나**" | 배포판 벤더의 판정 | 백포트 오탐 제거 + 아직 수정본이 없는 건 `조치 불가` 로 분리 |
| **리눅스 커널 CNA** | "이 **커널 버전**에 수정본이 들어 있나" | 업스트림(kernel.org)의 판정 | 커널 CVE 판정 — 배포판 밖의 커널(라즈베리·자체빌드)까지 |
| **SCAP Security Guide** | "이 **설정**이 어느 기준에 어긋나나" | 검증된 보안설정 룰셋(오픈소스) | 보안설정 점검(CCE)의 **룰 정체·근거·기준 매핑**(CIS·NIST·STIG) |

## 보안설정 점검(CCE)은 왜 SSG 에 묶나

취약점(CVE)은 "취약한 버전" 이지만, CCE 는 "잘못된 설정" 이다. 그런데 **무엇이 잘못인지**를
우리가 정하면 그건 근거 없는 기준이다. MITRE CCE 사전은 2013년경 갱신이 끊겼고 KISA 가이드는
PDF/HWP 로만 나와서(API 없음) 그동안 룰을 코드에 직접 써 넣었다(cce.php 385줄).

SSG(ComplianceAsCode)는 오픈소스 룰셋이고, 룰마다 **CIS 벤치마크·NIST 800-53·STIG·PCI-DSS 참조**와
근거(rationale)를 갖는다. 그 카탈로그를 받아 우리 점검을 룰 ID 에 묶었다(32개 중 27개).
→ 화면이 "CIS 5.2.11 · NIST AC-17(a)" 처럼 **검증된 기준을 인용**한다.

**솔직한 한계**: 판정 로직(OVAL)까지 중앙에서 돌리진 못한다. OVAL 은 살아 있는 파일시스템을
프로브하는데, 우리는 에이전트가 보낸 사실만 갖고 있고 대상 서버엔 아무것도 설치하지 않는다.
그래서 룰의 **정체·근거·기준**은 SSG 가 갖고, **판정**은 수집값으로 우리가 한다.
대응 룰이 없는 5개 항목은 화면에 "자체 기준" 으로 그대로 드러낸다.

## 왜 배포판 벤더 소스가 따로 필요한가

배포판(데비안·RHEL)은 **버전을 안 올리고 패치만 백포트**한다. 그래서 업스트림 버전만 보면
이미 고쳐진 것도 취약해 보인다 — 이게 오탐 1순위였다(실측: HIGH 160건 중 73건).
그 판정은 **벤더만 할 수 있다.** 예전엔 대상 서버에서 `debsecan`·`dnf updateinfo` 로 긁어왔지만,
지금은 **중앙이 벤더 데이터를 직접 받는다**(에이전트는 사실만 수집한다 — 폐쇄망 서버엔 설치조차 못 한다).

**조치 가능 여부도 벤더가 답한다.** 데비안 트래커는 CVE 마다 "이 릴리스에 수정본이 나왔는가"
(debsecan `flags[3]=='F'`)를 준다. 실측(raspberrypi5-00): 트래커가 답한 호스트 1,025건 중
**708건이 수정본 없음**이었다 — HIGH 87건 중 지금 `apt upgrade` 로 고칠 수 있는 건 8건뿐인데
화면엔 다 섞여 있었다. 이제 나머지는 `조치 불가` 로 분리한다(Red Hat 은 `rhunfixed` 가 같은 일을 한다).

**우분투는 한 파일이 둘 다 준다.** Canonical 의 릴리스별 CVE OVAL 은 테스트에 조치 EVR(state)이
있으면 "그 버전 미만이 취약", state 가 없으면 "그 패키지가 있으면 취약"(= 아직 수정본 없음)이다.
그래서 억제와 조치 불가를 한 소스에서 얻는다 — RHEL 은 OVAL(수정본) + 미수정 CVE API 로 나뉜다.

반대 방향의 함정도 있다. OVAL·트래커는 **고쳐진 것만** 담는다. 벤더가 "안 고친다/아직 안 고쳤다"고
표시한 CVE 는 거기 없어서 통째로 안 보였다(실측 UBI8: Trivy 523건 중 514건). 이건 오탐이 아니라
미탐이고, **패치가 존재하지 않는** 종류다 — 그래서 등급은 그대로 두되 `조치 불가` 로 표시해
"지금 고칠 수 있는 것" 과 화면에서 분리한다. 섞으면 조치 불가 수백 건이 고칠 수 있는 몇 건을 덮는다.

## 커널은 왜 배포판이 아니라 업스트림이 판정하나

커널 패키지는 배포판 버전 체계 밖에 있는 경우가 많다. 라즈베리파이 OS 의 커널은
`linux-image-6.18.34+rpt-rpi-2712`(출처: Raspberry Pi Foundation)라서 데비안 트래커에도,
배포판 조치안(EVR)에도 **없다**. 매처는 서드파티 저장소 패키지를 "자동 판정 불가" 로 남기므로
(그렇게 안 하면 진짜 취약점을 숨긴다) 커널 CVE 가 통째로 살아남았다 —
실측 raspberrypi5-00: **LOW 2,069건 중 702건이 커널 하나**였고, 6.18 커널에 CVE-2004-0230(2004년
TCP 이슈)까지 붙어 있었다.

2024년부터 **커널 팀이 직접 CVE 를 발행한다**(kernel.org CNA). 레코드마다 "어느 stable 시리즈의
어느 버전에서 고쳤는가" 가 들어 있다.

```
{"version":"6.5",   "status":"affected"}                                  ← 6.5 부터 취약
{"version":"6.1.78","lessThanOrEqual":"6.1.*","status":"unaffected"}      ← 6.1.y 는 6.1.78 에서 수정
{"version":"6.8",   "lessThanOrEqual":"*",    "status":"unaffected"}      ← 메인라인 6.8 에서 수정
```

`uname -r` 로 잡은 **구동 커널의 업스트림 버전**(6.18.34)과 대조한다. **억제 방향으로만** 쓴다 —
내 스트림(6.18.y)에 수정본이 없으면 "다른 스트림에서 고쳐졌다"는 사실은 나와 무관하므로 억제하지 않는다.

**배포판 커널엔 적용하지 않는다.** RHEL 커널은 `5.14.0` 위에 백포트를 쌓은 것이라 업스트림 버전이
코드 내용을 대변하지 않는다 — "이 취약 코드는 6.1부터 들어갔다"를 그대로 믿으면 Red Hat 이 그 기능을
5.14 로 백포트한 경우를 "해당 없음" 으로 지운다(미탐). 배포판 커널은 트래커·OVAL 이 이미 정확히
판정하므로, 커널 CNA 는 **그들이 관할하지 않는 커널**(라즈베리·자체빌드)만 맡는다.

## 왜 이렇게 나누나

- **NVD / OSV — 무엇인지(기준 정보)**
  CVE 의 설명, CVSS 기본점수, 영향받는 제품·버전이 여기서 온다. OSV 는 배포판별
  패키지 버전 범위를 정확히 줘서 백포트 오탐을 걸러내는 데 쓴다(설치 버전에 실제로
  영향을 주는 것만 남긴다). NVD 는 전체 CVE(약 36만 건)의 원장 역할.

  > 외부 피드로 다 못 거르는 백포트는 **호스트 자신이 답을 갖고 있다** — 에이전트가 보낸
  > 패키지 changelog 의 CVE 수정 기록으로 2차 억제를 한다(피드가 아니라 수집물이 근거).
  > 상세: [`architecture.md` §2](architecture.md#2-매처-판정-로직--실제로-위험한가).

- **EPSS — 악용될 확률(예측)**
  CVSS 가 높아도 실제로 악용되는 취약점은 일부다. EPSS 는 "앞으로 30일 안에 악용될
  확률"을 0~1 로 준다. **정렬**에 쓴다 — 같은 심각도라면 EPSS 높은 것을 위로.

- **CISA KEV — 실제로 악용 중인지(확정 사실)**
  "이미 공격에 쓰이고 있다"가 확인된 목록이다. 예측(EPSS)이 아니라 사실이므로
  **등급을 끌어올리는 결정타**로 쓴다. 외부에 노출된 자산에서 KEV 취약점이 발견되면
  곧바로 CRITICAL 로 올린다.

- **KISA — 한국 맥락(지역 보완)**
  보호나라(boho.or.kr) 국내 보안공지. 해외 피드(NVD/OSV/KEV)가 다루지 않거나 늦는
  국내 이슈를 보완한다. 공지 본문까지 수집해 상세 페이지(`advisory.php`)에서 보여주고,
  본문에서 CVE 를 추출해 findings 와 연계한다.

## 우선순위에 어떻게 반영되나

매처(matcher)가 위 신호를 합쳐 최종 등급을 낸다.

```
기본 심각도(CVSS, NVD/OSV)
  + 런타임 노출 맥락(외부노출 / 로컬리스닝 / 실행중 …)
  + KEV 등재 여부(실제 악용) → 한 단계 상향
  + EPSS(악용확률) → 같은 등급 내 정렬
= 최종 우선순위
```

핵심 규칙: **외부노출 + KEV = CRITICAL**. "무엇인지(NVD/OSV)"만으로 정하지 않고,
"실제로 악용되는가(KEV)"와 "우리 환경에 노출됐는가(런타임)"를 함께 본다.

## 수집 주기 (기본값)

| 커넥터 | 타입 | 주기 | 비고 |
|---|---|---|---|
| CISA KEV | kev | 24시간 | 악용 목록 |
| 데비안 보안 트래커 | debtracker | 24시간 | 릴리스별 "아직 취약" 목록(zlib 1.6MB). 대상 서버에 debsecan 불필요 |
| RHEL 계열 벤더 권고(OVAL) | rhoval | 24시간 | Red Hat/Alma/Oracle OVAL(bz2). 스트림별 조치 EVR — el9_2 와 el9_4 를 구분한다. Oracle 은 전 릴리스가 한 파일이라 `<platform>` 으로 가른다 |
| Red Hat 미수정 CVE | rhunfixed | 24시간 | 설치된 컴포넌트만 조회. 한 번 확인한 CVE 는 캐시(재조회 안 함) |
| 우분투 보안 OVAL | ubuntuoval | 24시간 | 릴리스별 CVE OVAL(noble 7.4MB bz2). 조치 EVR + 아직 수정본 없음 |
| 리눅스 커널 CNA | kcve | 24시간 | kernel.org vulns.git 스냅샷(20MB). CVE 12,000건의 스트림별 수정 버전 |
| SCAP Security Guide | ssg | 7일 | 룰셋은 릴리스 단위로만 바뀐다. tarball 9MB → 룰 2,493개 |
| OSV.dev | osv | 6시간 | 보유 CVE 의 영향 버전 |
| NVD 2.0 | nvd | 6시간(interval) | **수정일(lastMod) 기준** — 뒤늦게 CVSS 붙는 CVE 도 따라잡음 |
| KISA 보안공지 | kisa | 12시간 | 국내 공지 + 본문 |
| FIRST EPSS | epss | 매일 05:00 | 보유 CVE 의 악용확률 갱신 |

- NVD 는 발행일이 아니라 **수정일** 기준으로 수집한다. 예전에 발행된 CVE 에 나중에
  CVSS·설명이 붙는 경우가 흔한데, 발행일 기준이면 그 갱신을 영원히 놓친다.
- 전체 이력(약 36만 건)은 주기 수집이 아니라 `bin/backfill_nvd.php` 로 1회 채운다.
- KISA 는 RSS 3종(보안공지·취약점정보·경보단계)을 읽는데, **RSS 가 피드당 최신 10건만** 준다
  (= 매 수집 `fetched=30`). 이미 저장된 건이면 `upserted=0` 이 정상이다. 과거 공지는 RSS 에
  아예 없으므로 `bin/backfill_kisa.php` 로만 채울 수 있다.
- NVD API 키는 DB(`tb_feed_connectors.connection_json.api_key`)에만 두고 코드·저장소에
  두지 않는다. 키가 있으면 요청 제한이 완화된다(없어도 동작, 느릴 뿐).

커넥터 설정·수동 실행·미리보기는 웹 UI `커넥터 관리(connectors.php)` 에서 한다.
