# 핵심 로직 3축 해설

이 문서는 vuln-agent 의 **판정 정확도를 좌우하는 세 축**을 코드 기준으로 설명한다.
읽는 사람이 코드를 열지 않고도 "왜 이렇게 짰는지 · 어디가 틀릴 수 있는지 · 어떻게 검증하는지"를
말로 설명할 수 있게 하는 것이 목적이다. 전체 구조는 [`docs/dev/architecture.md`](architecture.md)
가 정본이고, 여기서는 그중 세 곳만 깊게 판다.

| 축 | 한 줄 요약 | 정본 파일 |
| --- | --- | --- |
| ① 버전 비교 | "설치본이 조치본 이상인가" 를 배포판 규칙대로 판정 | `server/src/vercmp.php` |
| ② SCA/SBOM 매칭 | 수집된 패키지를 CVE 에 잇고, 오탐을 5겹으로 걷어냄 | `server/src/matcher.php` + `server/src/matcher/` |
| ③ 에이전트 서명 검증 | 자동 업데이트되는 스크립트가 **커밋 시점** 서명과 일치하는지 확인 | `agent/install-agent.sh` · `deploy/agent_sign.sh` |

## ① 버전 비교 — `server/src/vercmp.php`

### 왜 이게 어려운가

매칭의 마지막 판정은 항상 "설치 버전 ≥ 조치 버전이면 이미 패치됨" 한 줄이다
(`server/src/matcher/decide.php:96`). 이 한 줄이 틀리면 결과가 통째로 뒤집힌다 —
낮게 보면 이미 고친 것을 취약하다고 띄우고(오탐), 높게 보면 취약한 것을 패치됐다고 지운다(미탐).

PHP 의 `version_compare` 로는 배포판 버전을 비교할 수 없다. 파일 머리말
(`server/src/vercmp.php:7-14`)이 세 가지 실패를 명시한다.

| 순진한 구현 | 무엇이 틀리나 |
| --- | --- |
| 문자열 비교 | `1.1.1f-1ubuntu2.19` < `1.1.1f-1ubuntu2.9` — `'1' < '9'` 라서 19 가 9 보다 작아진다 |
| 단순 숫자 비교 | `1:1.1.1` vs `2.0` — 에포크(`1:`)를 못 읽어 2.0 이 최신이 된다. 실제로는 에포크가 우선이다 |
| `version_compare` | `1.0~rc1` 을 `1.0` 보다 **최신**으로 본다. dpkg 규칙에서 틸드는 무엇보다 이전이다 |
| 릴리스 무시 | `1.1.1f-1ubuntu2.19` 의 `-1ubuntu2.19` 를 버리면 백포트 보안패치를 못 알아본다 |

그래서 dpkg(Debian policy §5.6.12)와 rpm(rpmvercmp)의 알고리즘을 **각각 그대로 옮겨** 두 개의
비교기를 따로 뒀다. 두 규칙은 문자 순서와 `^` 처리가 미묘하게 달라 하나로 합치지 않는다
(`server/src/vercmp.php:13-14`).

### 데이터 흐름

버전 비교기는 두 지점에서 불린다 — **수집 시점**(피드가 조치안을 고를 때)과 **판정 시점**
(억제 게이트).

1. 피드 수집: OSV 응답의 취약 구간에서 "설치 버전이 포함된 구간의 fixed 경계"를 고를 때
   (`server/src/feeds/osv.php:51` `vg_osv_range_fixed` → 내부에서 `vg_ver_cmp`)
2. 그 결과가 `tb_cve_affected_package.fixed_version` 으로 저장된다 (`server/src/feeds/upsert.php:96`)
3. 매칭 시점: 후보 CVE 마다 `vg_ver_cmp(설치버전, 조치버전, 매니저)` (`server/src/matcher/decide.php:97`)
4. `>= 0` 이면 억제 → `tb_suppressed_finding` 으로 빠진다(위험 집계에서 제외)

즉 **같은 비교기가 수집과 판정 양쪽에 쓰인다.** 한쪽만 바꾸면 "피드는 취약하다고 저장했는데
매처는 패치됐다고 지운다" 같은 어긋남이 생긴다.

### 핵심 함수와 위치

| 함수 | 위치 | 책임 한 가지 |
| --- | --- | --- |
| `vg_deb_order` | `server/src/vercmp.php:18` | dpkg 문자 순서 하나를 정수로 (`~` < 없음 < 알파벳 < 기호) |
| `vg_deb_cmp_frag` | `server/src/vercmp.php:28` | upstream/revision **한 조각**을 비숫자 구간·숫자 구간 번갈아 비교 |
| `vg_deb_cmp` | `server/src/vercmp.php:51` | `[epoch:]upstream[-revision]` 로 쪼개 에포크 → upstream → revision 순으로 판정 |
| `vg_rpm_cmp_frag` | `server/src/vercmp.php:71` | rpmvercmp 의 영숫자 구간 비교 + `~`(이전)·`^`(이후) 특별 취급 |
| `vg_rpm_cmp` | `server/src/vercmp.php:126` | rpm EVR 비교. `(none)` 에포크를 0 으로 정규화 |
| `vg_lang_cmp` | `server/src/vercmp.php:159` | semver/PEP440 — 여기서만 `version_compare` 를 쓴다 |
| `vg_ver_cmp` | `server/src/vercmp.php:168` | 매니저 이름으로 위 넷 중 하나를 고르는 유일한 진입점 |

`vg_ver_cmp` 의 분기는 다섯 갈래다(`server/src/vercmp.php:170-183`).

```php
case 'rpm':      return vg_rpm_cmp($a, $b);
case 'pip': case 'npm': case 'gem': case 'composer': return vg_lang_cmp($a, $b);
case 'go':       return vg_lang_cmp(ltrim($a, 'vV'), ltrim($b, 'vV'));
case 'upstream': return vg_lang_cmp($a, $b);
default:         return vg_deb_cmp($a, $b);   // dpkg + apk
```

- `go` 는 앞의 `v` 만 뗀다 — 수집값은 `v1.2.3`, OSV 조치안은 `1.2.3` 이라 그대로 비교하면 어긋난다.
- `apk`(알파인)는 별도 비교기가 없다. `1.2.3-r0` 이 upstream-revision 꼴이라 dpkg 규칙이
  그대로 맞아 `default` 로 떨어진다(`server/src/vercmp.php:181-183`).

### 경계 사례와 실패 모드

| 경계 사례 | 지금 어떻게 막고 있나 |
| --- | --- |
| 선행 0 (`1.007` vs `1.7`) | 숫자 구간 진입 전에 `'0'` 을 건너뛴 뒤 **자릿수 먼저** 비교 (`vercmp.php:40-44`) |
| rpm 에포크가 `(none)` | `ctype_digit` 이 아니면 0 으로 본다 — `rpm -qa` 가 실제로 `(none)` 을 찍는다 (`vercmp.php:131-133`) |
| 피드 조치안에 릴리스가 없음 | 한쪽만 릴리스가 있으면 **릴리스를 비교하지 않는다** (`vercmp.php:146-147`). 비교하면 `1.0` 이 `1.0-1` 보다 낮아져 오탐이 된다 |
| 언어 패키지에 EVR 비교기를 쓰면 | `1.0.0-rc1` 의 `-rc1` 을 데비안 리비전으로 읽어 정식 릴리스보다 **최신**으로 판단 → 취약한데 패치됨으로 오억제 = **미탐**. 그래서 `vg_lang_cmp` 를 따로 뒀다 (`vercmp.php:151-158`) |
| 업스트림 버전 행과 배포판 EVR 을 섞어 비교 | 비교기가 아니라 **호출부**에서 막는다 — `vg_eco_is_distro()` 가 배포판 형식 행만 참을 돌려주고(`server/src/distro.php:259`), 아니면 `fixed` 를 `null` 로 떨어뜨려 버전 판정 자체를 하지 않는다(`server/src/matcher/candidates.php:58`). `nginx 1.21.0`(업스트림) vs `1:1.20.1-14.el9_2`(EVR)를 비교하면 에포크 때문에 설치본이 더 최신이 되어 미탐이 난다 |

**지금 테스트가 덮지 않는 곳**: `tests/vercmp_test.php` 의 케이스 그룹은 `deb` · `rpm-frag` ·
`rpm-evr` · `lang` 네 개뿐이다(파일 29·47·62·72행). `go`(v 접두 제거)·`upstream`·`apk` 분기는
단위 테스트에 케이스가 없다 — dpkg/semver 로 위임하는 얇은 분기라서지만, 회귀를 기계로 잡지는
못한다.

### 어떻게 검증하는가

호스트 PHP 는 7.2 라 8.x 문법을 오탐한다. 컨테이너로 돌린다.

```bash
MSYS_NO_PATHCONV=1 docker run --rm -v "$(pwd -W):/w" -w /w php:8.3-cli php tests/vercmp_test.php
# → vercmp: 전체 통과   (2026-08-21 실행 확인, exit 0)
```

기대값은 추측이 아니라 실제 도구에서 뽑았다(`tests/vercmp_test.php:7-10`):
`dpkg --compare-versions` 와 `rpm --eval '%{lua:print(rpm.vercmp(A,B))}'`, 언어 패키지는
npm `semver.compare`. 이 테스트는 `tests/smoke.sh:342` 가 서버 없이 앞단에서 먼저 돌린다.

## ② SCA/SBOM 매칭 — `server/src/matcher.php` + `server/src/matcher/`

### 왜 이게 어려운가 / 왜 이 설계인가

"패키지 이름이 같으면 CVE 를 붙인다" 는 순진한 구현은 네 가지로 무너진다. 각각 실측 근거가
코드 주석에 남아 있다.

1. **생태계가 섞인다.** OS 의 `curl` 과 npm 의 `curl` 은 다른 물건이다
   (`server/src/distro.php:92-93`). 우분투 24.04 호스트에 20.04 의 조치안이 붙기도 한다
   (`server/src/feeds/osv.php:34-37`).
2. **소스 패키지가 곱해진다.** 커널 소스 `linux` 하나에서 바이너리가 21개 나오는데,
   `source_pkg` 가 같다는 이유로 커널 CVE 369건이 전부에 매달려 **LOW 7,925건**이 됐다
   (`server/src/distro.php:216-217`). 헤더·빌드도구엔 커널 코드가 없다.
3. **백포트를 못 읽는다.** 배포판은 버전을 안 올리고 패치만 얹는다. 버전만 보면 "취약"이지만
   실제로는 고쳐져 있다 — 이게 오탐의 큰 덩어리다.
4. **0건이 "안전"으로 읽힌다.** 피드가 모르는 배포판이면 후보 CVE 자체가 없어 조용히 0건이
   된다(`server/src/distro.php:15-16`). 그래서 `vg_distro_unsupported()` 가 ingest 응답에
   경고를 실어 보낸다(`server/public/ingest.php:370`).

설계의 뼈대는 **"매칭 범위 교정"과 "증거 기반 억제"를 분리한 것**이다. 헤더 패키지에서 커널
CVE 를 떼는 것은 억제가 아니라 범위 교정이고(취약 코드가 없으므로 미탐이 아니다), 백포트로
이미 고쳐진 건은 억제라서 `tb_finding` 이 아니라 `tb_suppressed_finding` 으로 따로 남긴다 —
지우지 않고 근거와 함께 보관한다(`server/src/matcher.php:153`).

### 데이터 흐름

| 단계 | 무엇이 일어나나 | 코드 |
| --- | --- | --- |
| 1. 수집 | 에이전트가 OS 패키지(TSV)·언어 패키지·컨테이너 내부 패키지·SBOM·런타임 노출을 한 JSON 으로 POST | `agent/vuln-inventory-agent.sh:2212-2217` 외 |
| 2. 파싱 | 매니저별 TSV → 행 배열. dpkg 상태가 `ii` 가 아닌 행(`rc` = 제거됨·설정만 남음)은 버린다 | `server/src/ingest/packages.php:16`·`28` |
| 3. 저장 | `tb_package` 등에 트랜잭션으로 저장. 직전과 내용이 같으면 새 스캔을 만들지 않는다 | `server/public/ingest.php:232`·`241` |
| 4. 피드 조회 | OSV 커넥터가 **그 스캔이 실제로 가진 패키지**를 `querybatch` 로 조회해 `tb_cve_affected_package` 를 채운다 | `server/src/feeds/osv.php:161`·`185`·`244` |
| 5. 매칭 | `vg_match_scan()` — 신호 → 카탈로그 → 근거 → 후보 → 판정 | `server/src/matcher.php:76` |
| 6. 쓰기 | 결과 지문이 이전과 같으면 **한 줄도 쓰지 않는다** | `server/src/matcher.php:180-186` |

수집 직후 `ingest.php:337` 이 `vg_match_scan()` 을 바로 부르고, 피드가 갱신될 때는
`vg_rematch_scan_ids()`(`server/src/matcher.php:275`)가 고른 **호스트별 최신 2건**만 다시 돈다.

`vg_match_scan` 안의 호출 순서가 곧 의존 방향이다(`server/src/matcher.php:33-41`):

```
classify(등급) → signals(원시 신호) → catalog(CVE) → evidence(억제 근거)
              → candidates(패키지 단위 후보·맥락) → decide(억제 게이트)
```

### 핵심 함수와 위치

| 함수 | 위치 | 책임 한 가지 |
| --- | --- | --- |
| `vg_load_scan_signals` | `server/src/matcher/signals.php:20` | 이 스캔의 원시 신호(스캔 메타·컨테이너·패키지·노출·프로세스)를 읽기만 한다 |
| `vg_load_cve_catalog` | `server/src/matcher/catalog.php:25` | KEV 집합 + **이 스캔이 가진 패키지 이름만** 의 영향 인덱스. 이름 단위 static 캐시 |
| `vg_load_suppression_evidence` | `server/src/matcher/evidence.php:20` | 억제 근거(changelog·errata·debsecan·벤더 OVAL)와 억제취소 신호(재시작 필요)를 모은다. 판정은 안 한다 |
| `vg_match_pkg_candidates` | `server/src/matcher/candidates.php:22` | 패키지 하나에 붙는 후보 CVE 집합 — **패키지↔CVE 조인 그 자체** |
| `vg_match_pkg_context` | `server/src/matcher/candidates.php:89` | 그 패키지의 모든 CVE 에 공통인 맥락(재시작·재부팅·서드파티·런타임 노출)을 한 번만 계산 |
| `vg_classify` | `server/src/matcher/classify.php:39` | 런타임 상태 7종 → 등급(LOW~CRITICAL) + 사람이 읽을 근거 |
| `vg_match_decide_cve` | `server/src/matcher/decide.php:29` | 후보 CVE 1건의 최종 판정. **억제 게이트 전부가 여기 한 함수** |
| `vg_match_fingerprint` | `server/src/matcher.php:51` | 판정 결과의 지문 — 같은 결과면 같은 지문이어야 한다 |

**등급 산정**(`classify.php:39-71`)은 억제와 축이 다르다. 노출 상태 7종
(EXTERNAL / LAN / FILTERED / LISTENING / RUNNING / LOADED / INSTALLED)을 레벨 1~3 으로
환산하고, KEV 등재면 한 단계 올린다(최대 CRITICAL). `FILTERED` 판정이 없으면 방화벽 뒤의
내부 서비스가 전부 HIGH/CRITICAL 로 뜬다(`classify.php:49-50`).

**억제 게이트**(`decide.php`)는 순서가 곧 우선순위다. 먼저 걸리는 조건이 이기고 뒤는 평가되지
않는다. 이 순서를 재배열하면 오탐/미탐이 즉시 바뀐다(`decide.php:8-10`).

| 순서 | 게이트 | 위치 | 억제 사유 |
| --- | --- | --- | --- |
| 0 | 실행 중이 아닌 커널 | `decide.php:40` | 설치만 된 커널 이미지 — 부팅해야 활성화된다 |
| 0' | 커널 CNA(kernel.org) | `decide.php:57` | 업스트림이 "이 구동 버전엔 수정본이 들어 있다"고 답함. **배포판 커널엔 적용 안 함** |
| — | 억제 보류 ①런타임 | `decide.php:70` | 재시작·재부팅 대기 — **근거 종류를 가리지 않고** 전부 막는다 |
| — | 억제 보류 ②서드파티 | `decide.php:85`·`90` | 배포판 조치안과 버전 체계가 달라 **버전 비교 계열만** 막는다 |
| ① | 버전 | `decide.php:96` | 설치 ≥ 조치 |
| ② | 배포판 보안 트래커(debsecan) | `decide.php:109` | 트래커가 "해당 없음"으로 판정 |
| ③ | 벤더 OVAL(RHEL 계열) | `decide.php:124` | 설치 EVR ≥ errata EVR |
| ④ | 적용된 벤더 보안권고(errata) | `decide.php:135` | 이 빌드에 적용된 권고가 그 CVE 를 고침 |

## ③ 에이전트 서명 검증 — `agent/` · `deploy/agent_sign.sh`

### 왜 이게 어려운가 / 왜 이 설계인가

에이전트는 **자기 자신을 자동으로 갱신한다.** 노드가 폴링할 때 중앙이 "새 버전이 있다"고
알려주면, 노드가 스크립트를 내려받아 자기를 교체한다. 이 경로는 곧 **원격 코드 실행 경로**다 —
중앙을 장악한 공격자가 임의 스크립트를 모든 노드에 root 로 실행시킬 수 있다.

sha256 만으로는 이걸 못 막는다. 그 해시 값을 **배포 파일과 같은 웹 프로세스가 즉석 계산해서**
응답에 싣기 때문이다(`server/src/agentupdate.php:45`). 웹 티어가 침해되면 공격자가 준비한
파일의 해시를 그대로 "검증 통과"로 만들 수 있다. 즉 sha256 은 **전송 중 손상만** 잡는다
(`agent/install-agent.sh:167-170`).

그래서 방어선을 **커밋 시점**으로 옮겼다. 서명은 유지보수자의 로컬 개인키로 커밋 전에 만들고,
`.sig` 를 스크립트와 같은 커밋에 넣는다. **PHP 는 그 파일을 읽기만 하고 절대 서명을 만들지
않는다**(`agent/install-agent.sh:170`, `server/src/agentupdate.php:16-17`). 개인키는 저장소에도,
Docker Secrets 에도 두지 않는다 — 웹 컨테이너가 읽을 수 있는 곳에 있으면 이 체계 전체가
무의미해진다(`deploy/agent_sign.sh:16-21`). `agent_sign.sh` 는 개인키 경로가 저장소 안이면
아예 거부한다(`deploy/agent_sign.sh:49-55`).

알고리즘은 Ed25519 이고, 서명 대상은 스크립트 **원본 바이트 전체**다(`openssl pkeyutl -sign -rawin`,
`deploy/agent_sign.sh:63`).

### 데이터 흐름

| 단계 | 어디서 | 무엇이 일어나나 |
| --- | --- | --- |
| 1. 서명 | 유지보수자 로컬 | `bash deploy/agent_sign.sh ~/agent-signing.key` → `agent/vuln-inventory-agent.sh.sig`(64바이트 raw) 생성. `.sh` 와 `.sig` 를 같은 커밋에 |
| 2. 공개키 고정(pin) | 노드 최초 설치 | `install-agent.sh` 가 `agent-dl.php?f=vuln-inventory-agent.pub` 로 공개키를 받아 `$PREFIX/etc/agent-update.pub`(0600)에 **한 번만** 고정 (`install-agent.sh:622-665`) |
| 3. 폴링 | 노드 → 중앙 | `vuln-inventory-agent.sh --poll-once` 가 자기 `SCRIPT_VERSION` 을 실어 `agent-poll.php` 를 GET (`agent/vuln-inventory-agent.sh:166`) |
| 4. 제안 | 중앙 | 배포 파일 버전이 더 높으면 `update_version`·`update_sha256`·`update_download_path`·`update_signature`(base64) 를 응답에 싣는다 (`server/public/agent-poll.php:44-52`) |
| 5. 검증·교체 | 노드 `run.sh` | 다운로드 → sha256 → **Ed25519 서명** → `bash -n` → 백업 → 원자적 `mv` (`install-agent.sh:177-300`) |
| 6. 자기점검 | 노드 다음 실행 | `bash -n` + `--help` 실행이 통과해야 적용 확정. 실패하면 `.bak` 으로 롤백 (`install-agent.sh:308`) |
| 7. 보고 | 노드 → 중앙 | 직전 업데이트 결과 1줄을 **다음 폴링 GET 에 실어** 보고한다(새 인바운드 경로를 만들지 않는다) |

**중앙→노드 인바운드 경로가 없다.** 노드가 항상 능동적으로 물어보고 받아 간다. 이 원칙 때문에
업데이트도 폴링 응답에 얹는 형태가 됐다.

> 주의: 5·6 단계 코드의 인용 줄번호는 `agent/install-agent.sh` 기준이지만, 그 코드는 설치기가
> heredoc 으로 **생성하는** `$PREFIX/bin/run.sh`(기본 `/opt/vuln-agent/bin/run.sh`) 안에서 돈다
> (`install-agent.sh:116` `vg_write_runner`).

### 핵심 함수와 위치

| 함수 | 위치 | 책임 한 가지 |
| --- | --- | --- |
| `vg_agent_release_info` | `server/src/agentupdate.php:19` | 배포 파일에서 버전·sha256·서명(base64)을 읽는다. DB 에 따로 저장하지 않는다 — **파일이 곧 정본** |
| `vg_poll_once` | `agent/vuln-inventory-agent.sh:166` | 중앙에 한 번 물어보고 `키=값` 지시문을 stdout 으로. 토큰은 절대 싣지 않는다 |
| `do_update` | `agent/install-agent.sh:177` | 내려받아 4중 검증 후 원자적 교체 |
| `fail_update` | `agent/install-agent.sh:155` | 실패를 조용히 삼키지 않고 사유 토큰을 파일에 남긴다(다음 폴링에 보고) |

`do_update` 안의 검증 순서(`install-agent.sh:231-295`):

```
sha256 (231-241) → openssl 존재 (247) → OpenSSL 3.0+ 판정 (257-262)
  → 공개키 핀 존재 (266) → 서명 존재 (270) → base64 (274)
  → openssl pkeyutl -verify -rawin (280)
→ bash -n 문법검사 (286) → .bak 백업 (290) → mv 원자적 교체 (295)
```

`do_update` 는 이 한 가지 이유로 **`run.sh` 에 남는다**: 자기를 갱신하는 코드가 갱신 대상 안에
있으면 교체 도중 실패했을 때 되돌릴 주체가 사라진다(닭과 달걀, `install-agent.sh:165-166`).
반대로 응답 파싱은 본체(`vuln-inventory-agent.sh`)에 있다 — `run.sh` 는 자동 갱신되지 않아서,
거기 두면 새 응답 필드가 기존 노드에 **영원히 도달하지 못한다**
(`agent/vuln-inventory-agent.sh:124-129`, 실제로 무결성 검사 명령이 그렇게 조용히 무시됐다).

## 부록: 세 축이 만나는 곳

- **①이 ②에 쓰인다.** 억제 게이트 ①번(`decide.php:97`)과 OSV 조치안 선택(`osv.php:51`)이
  같은 `vg_ver_cmp` 를 부른다. 버전 비교가 틀리면 매칭 결과가 통째로 틀린다 — 그래서
  "매처 오탐 1순위" 다.
- **③이 ②의 입력을 지킨다.** 매칭의 재료는 전부 에이전트가 보낸 것이다. 에이전트 스크립트가
  바꿔치기당하면 판정 로직이 아무리 정확해도 결과가 거짓이 된다.
- 세 축 모두 같은 원칙 위에 있다: **모르면 억제하지 않는다.** 판단 근거가 없을 때 조용히
  0건으로 만들지 않고 경고·`no_fix`·"자동 판정 불가"로 드러낸다. 미탐(숨김)이 오탐(시끄러움)
  보다 훨씬 비싸다는 판단이다.
