# 에이전트 리소스 프로파일 — CPU·메모리 얼마나 쓰나

> 문서 기준: 2026-08-20 · 에이전트 3.17. "다른 서버에도 안심하고 깔 수 있나?"에 숫자로 답하는 문서다.
>
> **실측표의 측정 시점은 2026-08-04 · 에이전트 3.8 이다.** 그 뒤의 속도 개선은 이 표에
> **반영되지 않았다** — 재측정 없이 숫자를 손대지 않는다(기록은 아래 아카이브 포인터).
> 지금 값은 [`tests/agent-bench.sh`](../../tests/agent-bench.sh) 를 그 서버에서 다시 돌려 뽑는다
> (맨 아래 “재측정 방법”). 최신 실행값 자체는 자산 상세에서 본다.

## 한 줄 결론

에이전트 서비스는 10초마다 명령을 poll 하는 상시 경량 데몬이고, 무거운 수집은 설정 주기(기본
60분, 웹에서 변경 가능)에만 도는 배치다. 수집 프로세스는 `nice 19`+`ionice idle` 로 항상 양보하고
명령별 20초 타임아웃·섹션당 512KB 출력 상한·중복실행 방지(flock)가 걸려 있으며, **읽기 전용**이라
시스템을 바꾸지 않는다. 피크 메모리는 수십 MB. 기본값(`normal` 티어)은 커널이 한 코어의 10%·메모리
300M 을 강제하므로 4코어 호스트 전체 용량 기준 CPU 는 최대 약 2.5%이고, 두 상한은 호스트별
**속도 티어**로 조절한다(아래 절).

## 설계상 이미 걸려 있는 상한

| 장치 | 코드 | 효과 |
|---|---|---|
| `nice 19` | `renice -n 19 -p $$` | CPU 경합 시 최저 우선순위 → 다른 프로세스에 양보. 유휴 CPU만 쓴다 |
| `ionice idle` | `ionice -c3` | 디스크 I/O 도 최저 우선순위 → DB·앱 디스크를 방해 안 함 |
| 명령별 타임아웃 | `timeout -k 2 20s` (`CMD_TIMEOUT`) | 느린 명령 하나가 폭주해도 20초에 끊김 |
| 출력 바이트 상한 | `head -c 512KB` (`MAX_BYTES`) | 거대한 출력이 메모리·페이로드를 부풀리지 못함 |
| 중복 실행 방지 | `flock -n` | cron 겹침으로 두 개가 동시에 도는 사고 차단 |
| 프로세스 순회 안전장치 | `PROC_SCAN_TIMEOUT`(기본 180초, 30~3600 검증) | 프로세스가 수천 개여도 이 시간에 중단. 잘리면 `meta.processes_truncated=1` 로 알린다 — 조용히 통과하지 않는다 |
| cgroup 하드리밋 | 기본값 → `systemd-run` | 커널이 CPU·MEM 상한을 **강제**(초과 불가). 기본 CPU≤한 코어의 10% · MEM≤300M, 티어에 따라 CPU 5~80% · MEM 200~1024M |
| JSON 조립 상한 | `PACKAGING_TIMEOUT`(기본 120초) | 조립이 폭주해도 끊고 실패로 마감 — 웹에 94% running 이 영구히 남지 않게. 티어에 따라 90~300초 |
| 무결성 검증 상한 | `VERIFY_TIMEOUT`(기본 300초) | `rpm -Va`/`dpkg --verify` 는 설치된 **모든 파일**을 해시한다 → **기본 꺼짐**(`--verify-files` 일 때만). 잘리면 부분 결과로 표시해 보낸다 |
| 장시간 단계 하트비트 | `progress_heartbeat`(수집 5초) · 조립 루프(10초) | `collect_pkg_origins`(apt-cache)처럼 수 분 걸릴 수 있는 단계도 진행 신호를 계속 보낸다 |

읽기 전용이라는 것도 리소스 안전에 중요하다 — 쓰기 락·재빌드·재시작을 유발하지 않으므로
측정값은 순수 "읽고 파싱하는" 비용뿐이다.

## 상한은 호스트마다 다르게 줄 수 있다 — 속도 티어

CPU·메모리·조립 타임아웃 세 상한은 **호스트별 속도 티어**로 정한다. 정의처는
[`server/src/agentspeedtier.php`](../../server/src/agentspeedtier.php) 하나이고, 화면(호스트 상세
수집 제어) → `tb_host.agent_speed_tier` → `agent-poll.php` → `run.sh` 의 env 로 전달된다.

| 티어 | `CPU_QUOTA` | `MEM_MAX` | `PACKAGING_TIMEOUT` |
|---|---|---|---|
| `very_fast` | 80% | 1024M | 300초 |
| `fast` | 40% | 512M | 200초 |
| `normal`(기본) | 10% | 300M | 120초 |
| `slow` | 5% | 200M | 90초 |

- 상한을 올린다고 에이전트가 더 많이 쓰는 게 아니다 — cgroup 은 **못 넘게 막는 천장**이다.
  피크가 천장에 닿는 호스트에서만 티어를 올린다(그러면 조립이 OOM 으로 죽지 않는다).
- 반대로 극민감 호스트는 `slow`(CPU 5% · MEM 200M)로 낮춘다. 조립 타임아웃도 90초로 같이 줄어드니
  패키지가 많은 서버에선 조립 실패가 날 수 있다(세 값이 한 묶음이다).
- 티어가 노드에 반영되려면 그 노드의 `run.sh` 가 이 필드를 읽는 버전이어야 한다 — 자세한 건
  [`agent/README.md`](../../agent/README.md) 의 “속도 티어”·“갱신” 절.

지난 변경 기록(2026-08-19 프로세스 스캔 컷오프 설정화 · 2026-08-06 속도 개선·메모리 상한 추가)은
[`archive/에이전트-수집속도-변경기록.md`](archive/에이전트-수집속도-변경기록.md) 로 옮겼다.

## 부작용·안전성 감사 (포트/방화벽/서비스)

"포트를 죽이거나, 방화벽을 깨거나, 서비스를 내리는 일은 없나?" — **없다.** 소스 전수
grep 으로 검증했다(상태변경 명령이 하나도 없다).

| 항목 | 수치 | 근거 |
|---|---|---|
| **리스닝 포트 여는가** | **0개** | 에이전트는 어떤 포트도 bind/listen 하지 않는다. `ss -tulpn` 은 여는 게 아니라 **읽는다** |
| **아웃바운드 연결** | **≤1개** | `--send` 지정 시에만 중앙으로 curl POST 1회(TCP 클라이언트, `-m 30` 타임아웃). 미지정이면 0 |
| **방화벽 변경** | **0건** | firewalld/ufw/iptables/nft 를 `--list`/`status`/`-S`/`list ruleset` 로 **읽기만**. add·remove·reload·flush 전무 |
| **서비스 start/stop/restart/kill** | **0건** | `systemctl list-units/list-unit-files/--failed/list-timers` = 조회만. 변경 동사 없음 |
| **프로세스 kill** | **0건** | `kill`/`pkill`/`killall` 미사용. `/proc/PID/*` 를 **읽기만** |
| **시스템 파일 쓰기** | **0건** | 쓰기는 전부 `/tmp`(산출물·락·임시디렉터리) 또는 `-o` 로 지정한 경로뿐. 시스템 경로 수정 없음 |
| **권한 변경(chmod/chown)** | **0건** | 에이전트 본체엔 없음 |
| **우선순위 조정 대상** | 자기 자신만 | `renice`/`ionice` 는 `-p $$`(자기 PID)에만. 다른 프로세스 우선순위는 안 건드림 |

**읽기 전용 원칙**: 에이전트는 인벤토리를 *관측*할 뿐 *변경*하지 않는다. 방화벽 규칙을 읽는 건
"이 포트가 외부에 열렸나"를 판정하기 위한 것이고, 애매하면 **열림으로 보수적으로 간주**한다.

> **설치기(`install-agent.sh`)는 예외로 상태를 바꾼다** — 그게 목적이다. 단 범위는 (1)
> `/opt/vuln-agent/**` 파일 생성, (2) 자신의 systemd 유닛·타이머 작성 + `enable --now`, (3) 없으면
> crontab 항목 추가 뿐이고 **방화벽·포트·타 서비스는 건드리지 않는다**(grep 확인).
> 제거(`--uninstall`)는 이 세 가지만 정확히 되돌린다.

## 무엇이 비용을 좌우하나 (스케일링 규칙)

**메모리 피크의 1등은 jq다.** 마지막에 `jq -s reduce` 로 전 섹션을 한 번에 메모리에
올려 JSON 을 조립한다. 그래서 피크 RSS ≈ **전체 페이로드 크기에 비례**한다(위 표에서
jq 유무로 18MB↔62MB). 페이로드는 대부분 패키지 목록이므로:

- **피크 RSS ↑ 요인**: 설치 패키지 수, 실행 프로세스 수(런타임 노출/스테일 섹션), 컨테이너 내부
  패키지 수(`collect_containers`). 512KB×섹션 상한이 있어 유계다.
- jq 가 없으면 텍스트로 저장(피크 급감)하지만 **중앙이 파싱을 못 해 전송이 생략**된다 — 운영
  서버엔 jq 를 두는 게 정상 경로다.

**CPU 시간의 1등은 패키지 조회·changelog·프로세스 순회다.**

- `dpkg-query -W` / `rpm -qa` : 패키지 수에 비례(선형).
- `file_to_pkg` 의 `dpkg -S` : 프로세스가 로드한 `.so`→패키지 역조회. **조회 캐시**가
  있어 같은 라이브러리는 한 번만 친다 → 프로세스가 많아도 라이브러리 종류에 비례.
- changelog 단계: 13개 핵심 패키지만 대상(하드코딩)이라 **패키지 수와 무관하게 상수**. 가장 무거운
  축이지만 대상이 소수라 실측 수 초다(부담되면 `--no-changelog` — 백포트 억제가 약해져 비권장).
- 컨테이너가 많으면 `collect_containers` 가 컨테이너 수만큼 rootfs 패키지 DB 를 파싱.

**벽시계는 CPU 시간보다 항상 길거나 같다** — `nice 19`·`ionice idle` 때문에 서버가 바쁘면 대기하며
늘어난다. "서버에 부담"이 아니라 "양보하느라 느려짐"이다. **부담의 척도는 CPU 시간(초)이다.**

## 도입 판단 — 외삽하고, 실측으로 대체한다

| 서버 유형 | 패키지 수 | 예상 CPU 시간 | 예상 피크 RSS |
|---|---|---|---|
| 최소 컨테이너/슬림 | ~100 | 1~3s | 20~60MB |
| 일반 앱 서버 | 300~800 | 3~8s | 60~120MB |
| 풀 패키지 서버(개발/빌드) | 1500~3000 | 8~20s | 120~300MB |

순수 외삽(피크 RSS ∝ 페이로드, CPU ∝ 패키지 수)이라 **각 서버 실측으로 대체하라.**

- **안심 기준**: CPU 시간이 **한 자릿수 초** & 피크 RSS 가 **RAM 의 5% 미만**이면 안전(대다수).
  RAM 대비 피크가 5%를 넘으면 티어를 `slow`(MEM 200M)로 낮춰 천장을 조이고, 반대로 피크가 기본
  300M 천장에 닿는 서버(패키지 수천 개)는 티어를 올려야 조립이 OOM 으로 죽지 않는다. 극민감
  서버는 `--schedule daily` 로 빈도를 낮추거나 업무 시간을 피해 `OnCalendar` 를 잡는다.
- **서버가 1대뿐이어도 fleet 감을 잡을 수 있다**: 한 대에서 `full`/`--no-changelog`/`--limit`,
  root/비root 로 여러 점을 찍어 각 축의 기여를 분해하고, 위 스케일링 규칙으로 다른 규모에
  외삽한다. 접근 가능한 서버마다 같은 `--csv` 경로로 돌리면 이질적 fleet 의 분포가 한 파일에
  쌓이고, 중앙 DB `tb_scan.elapsed_seconds` 에는 이미 모든 보고 호스트의 소요시간(벽시계)이 있다.

## 재측정 방법

```bash
# 이 서버에서 (root 권장 — 실제 설치가 root systemd 서비스라 동일 조건)
sudo ./tests/agent-bench.sh                 # full·no-changelog 각 3회
sudo ./tests/agent-bench.sh --with-limit    # cgroup 리밋 시나리오 포함
sudo ./tests/agent-bench.sh --csv /tmp/fleet.csv   # 여러 서버 결과 누적

# 이미 설치된 에이전트를 대상으로
./tests/agent-bench.sh --agent /opt/vuln-agent/bin/vuln-inventory-agent.sh
```

측정 원리: GNU `time` 같은 추가 패키지 없이 `/proc` 만 쓴다 — 프로세스 트리 전체 RSS 를 0.2초마다
샘플링한 최댓값(피크), `utime+stime+cutime+cstime`(자식 포함 CPU), `/proc/uptime` 벽시계.
`--limit` 시나리오는 트리가 cgroup 스코프로 재부모화돼 `/proc` 추적이 부정확하므로 벽시계만
신뢰하고, 메모리·CPU 상한은 cgroup 이 보장한다.
