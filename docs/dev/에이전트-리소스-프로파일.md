# 에이전트 리소스 프로파일 — CPU·메모리 얼마나 쓰나

> "다른 서버에도 안심하고 깔 수 있나?"에 숫자로 답하는 문서.
> 실측은 [`tests/agent-bench.sh`](../../tests/agent-bench.sh) 로 각 서버에서 직접 뽑는다.

## 한 줄 결론

에이전트는 **데몬이 아니라 매시간 1회 수 초 돌고 끝나는 배치**다. `nice 19` +
`ionice idle` 로 다른 프로세스에 항상 양보하고, 명령별 20초 타임아웃·섹션당 512KB
출력 상한·중복실행 방지(flock)가 걸려 있다. **읽기 전용**이라 시스템을 바꾸지 않는다.
피크 메모리는 수십 MB, CPU는 수 초(1코어 기준)면 끝난다. 걱정되면 `--limit` 으로
커널이 CPU 25%·메모리 300M 를 강제하게 할 수 있다.

## 설계상 이미 걸려 있는 상한

| 장치 | 코드 | 효과 |
|---|---|---|
| `nice 19` | `renice -n 19 -p $$` | CPU 경합 시 최저 우선순위 → 다른 프로세스에 양보. 유휴 CPU만 쓴다 |
| `ionice idle` | `ionice -c3` | 디스크 I/O 도 최저 우선순위 → DB·앱 디스크를 방해 안 함 |
| 명령별 타임아웃 | `timeout -k 2 20s` (`CMD_TIMEOUT`) | 느린 명령 하나가 폭주해도 20초에 끊김 |
| 출력 바이트 상한 | `head -c 512KB` (`MAX_BYTES`) | 거대한 출력이 메모리·페이로드를 부풀리지 못함 |
| 중복 실행 방지 | `flock -n` | cron 겹침으로 두 개가 동시에 도는 사고 차단 |
| 프로세스 순회 안전장치 | `collect_processes` 90초 상한 | 프로세스가 수천 개여도 90초에 중단 |
| (옵션) cgroup 하드리밋 | `--limit` → `systemd-run` | 커널이 CPU≤25% · MEM≤300M 를 **강제**(초과 불가) |

읽기 전용이라는 것도 리소스 안전에 중요하다 — 쓰기 락·재빌드·재시작을 유발하지
않으므로, 측정값은 순수 "읽고 파싱하는" 비용뿐이다.

## 참조 실측치 (기준점, 대표값 아님)

Debian 12 · 20코어 · 7.7GB · **91패키지**(컨테이너, SSD 캐시 hot) 1회 측정:

| 시나리오 | 벽시계 | CPU 시간 | 피크 RSS | jq |
|---|---|---|---|---|
| full (실제 운영 그대로) | 3.7s | 3.1s | **61.6MB** | 있음 |
| no-changelog | 3.5s | 2.9s | 61.6MB | 있음 |
| full (jq 없음, 텍스트 출력) | 1.2s | 0.7s | **18.8MB** | 없음 |

> 이 숫자는 **작은 컨테이너 기준**이라 실제 서버로 그대로 옮기면 안 된다. 각 운영
> 서버에서 `tests/agent-bench.sh` 를 돌려 그 서버의 값을 뽑아라. 아래 스케일링 규칙으로
> 왜 서버마다 달라지는지 이해하고 외삽한다.

## 부작용·안전성 감사 (포트/방화벽/서비스)

"포트를 죽이거나, 방화벽을 깨거나, 서비스를 내리는 일은 없나?" — **없다.** 소스 전수
grep 으로 검증했다(상태변경 명령이 하나도 없다).

| 항목 | 수치 | 근거 |
|---|---|---|
| **리스닝 포트 여는가** | **0개** | 에이전트는 어떤 포트도 bind/listen 하지 않는다. `ss -tulpn` 은 여는 게 아니라 **읽는다** |
| **아웃바운드 연결** | **≤1개** | `--send` 지정 시에만 중앙으로 curl POST 1회(TCP 클라이언트, `-m 30` 타임아웃). 미지정이면 0 |
| **방화벽 변경** | **0건** | firewalld/ufw/iptables/nft 를 `--list`/`status`/`-S`/`list ruleset` 로 **읽기만**. add·remove·reload·flush 전무 |
| **서비스 start/stop/restart/kill** | **0건** | `systemctl list-units/list-unit-files/--failed/list-timers` = 조회만. 변경 동사 없음 |
| **프로세스 kill** | **0건** | `kill`/`pkill`/`killall` 미사용. `/proc/PID/*` 를 **읽기만** |
| **시스템 파일 쓰기** | **0건** | 쓰기는 전부 `/tmp`(산출물·락·임시디렉터리) 또는 `-o` 로 지정한 경로뿐. 시스템 경로 수정 없음 |
| **권한 변경(chmod/chown)** | **0건** | 에이전트 본체엔 없음 |
| **우선순위 조정 대상** | 자기 자신만 | `renice`/`ionice` 는 `-p $$`(자기 PID)에만. 다른 프로세스 우선순위는 안 건드림 |

**읽기 전용 원칙**: 에이전트는 인벤토리를 *관측*할 뿐 시스템을 *변경*하지 않는다. 방화벽
규칙을 읽는 건 "이 포트가 외부에 열렸나"를 판정하기 위한 것이고, 판정이 애매하면 **열림으로
보수적으로 간주**해 진짜 노출을 놓치지 않는다(규칙을 바꾸지 않는다).

> **설치기(`install-agent.sh`)는 예외로 상태를 바꾼다** — 그게 목적이기 때문이다.
> 단 바꾸는 범위는 (1) `/opt/vuln-agent/**` 파일 생성, (2) 자신의 systemd 유닛·타이머 작성 +
> `enable --now`, (3) 없으면 crontab 항목 추가 뿐이다. **방화벽·포트·타 서비스는 건드리지
> 않는다**(grep 확인). 제거(`--uninstall`)는 이 세 가지만 정확히 되돌린다.

## 무엇이 비용을 좌우하나 (스케일링 규칙)

**메모리 피크의 1등은 jq다.** 마지막에 `jq -s reduce` 로 전 섹션을 한 번에 메모리에
올려 JSON 을 조립한다. 그래서 피크 RSS ≈ **전체 페이로드 크기에 비례**한다(위 표에서
jq 유무로 18MB↔62MB). 페이로드는 대부분 패키지 목록이므로:

- **피크 RSS ↑ 요인**: 설치 패키지 수, 실행 프로세스 수(런타임 노출/스테일 섹션),
  컨테이너 내부 패키지 수(`collect_containers`). 512KB×섹션 상한이 있어 상한은 유계다.
- jq 가 없으면 텍스트로 저장(피크 급감)하지만 **중앙이 파싱을 못 해 전송이 생략**된다.
  운영 서버엔 jq 를 두는 게 정상 경로다 → 메모리 수십 MB 는 감수 대상.

**CPU 시간의 1등은 패키지 조회·changelog·프로세스 순회다.**

- `dpkg-query -W` / `rpm -qa` : 패키지 수에 비례(선형).
- `file_to_pkg` 의 `dpkg -S` : 프로세스가 로드한 `.so`→패키지 역조회. **조회 캐시**가
  있어 같은 라이브러리는 한 번만 친다 → 프로세스가 많아도 라이브러리 종류에 비례.
- changelog 단계: 13개 핵심 패키지만 대상(하드코딩)이라 **패키지 수와 무관하게 상수**.
  가장 무거운 축이지만 대상이 소수라 실측 수 초. 부담되면 `--no-changelog`(대신 백포트
  오탐 억제가 약해진다 — 권장하지 않음).
- 컨테이너가 많으면 `collect_containers` 가 컨테이너 수만큼 rootfs 패키지 DB 를 파싱.

**벽시계는 CPU 시간보다 항상 길거나 같다** — `nice 19`·`ionice idle` 때문에 서버가
바쁘면 대기하느라 벽시계가 늘어난다. 이건 "서버에 부담"이 아니라 "양보하느라 느려짐"이다.
**부담의 척도는 CPU 시간(초)이지 벽시계가 아니다.**

## 서버 규모별 대략 외삽

| 서버 유형 | 패키지 수 | 예상 CPU 시간 | 예상 피크 RSS |
|---|---|---|---|
| 최소 컨테이너/슬림 | ~100 | 1~3s | 20~60MB |
| 일반 앱 서버 | 300~800 | 3~8s | 60~120MB |
| 풀 패키지 서버(개발/빌드) | 1500~3000 | 8~20s | 120~300MB |

> 순수 외삽(피크 RSS ∝ 페이로드, CPU ∝ 패키지 수)이라 **각 서버 실측으로 대체하라.**
> RAM 대비 피크가 5%를 넘으면 `--limit`(MEM 300M 상한) 사용을 권한다.

## 서버 1대뿐이어도 "전체 서버" 감을 잡는 법

1. **한 대에서 변수를 바꿔 여러 점을 찍는다**: `full` / `--no-changelog` / `--limit`,
   root/비root. 각 축이 비용에 얼마나 기여하는지 분해된다.
2. **위 스케일링 규칙으로 다른 규모에 외삽**한다(패키지 수·코어 수만 알면 됨).
3. **접근 가능한 운영 서버마다 같은 `--csv` 경로로 돌려 누적**한다 → 이질적 fleet 의
   실제 분포가 한 CSV 에 쌓인다.
4. 중앙 DB `tb_scan.elapsed_seconds` 에는 이미 **모든 보고 호스트의 수집 소요시간**이
   쌓여 있다(벽시계). 규모 감을 잡는 보조 자료로 쓴다.

## 안심 기준 (도입 판단)

- CPU 시간이 **한 자릿수 초** & 피크 RSS 가 **RAM 의 5% 미만**이면 무조건 안전(대다수).
- 피크 RSS 가 부담스러우면 `sudo ... --limit` — 커널 cgroup 이 300M·CPU 25% 를 **강제**.
- 절대 안 건드려야 하는 극민감 서버라면 `--schedule daily` 로 빈도를 낮추거나 업무
  시간을 피해 `OnCalendar` 를 잡는다(설치기 `--schedule '*:0/30'` 등).

## 재측정 방법

```bash
# 이 서버에서 (root 권장 — 실제 설치가 root 타이머라 동일 조건)
sudo ./tests/agent-bench.sh                 # full·no-changelog 각 3회
sudo ./tests/agent-bench.sh --with-limit    # cgroup 리밋 시나리오 포함
sudo ./tests/agent-bench.sh --csv /tmp/fleet.csv   # 여러 서버 결과 누적

# 이미 설치된 에이전트를 대상으로
./tests/agent-bench.sh --agent /opt/vuln-agent/bin/vuln-inventory-agent.sh
```

측정 원리: GNU `time` 같은 추가 패키지 없이 `/proc` 만 쓴다. 에이전트 프로세스 트리
전체 RSS 를 0.2초마다 샘플링한 최댓값(피크), `utime+stime+cutime+cstime`(자식 포함
CPU), `/proc/uptime` 벽시계. `--limit` 시나리오는 트리가 cgroup 스코프로 재부모화되어
`/proc` 추적이 부정확하므로 벽시계만 신뢰하고, 메모리·CPU 상한은 cgroup 이 보장한다.
