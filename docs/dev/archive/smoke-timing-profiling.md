# 스모크 실행시간 프로파일링 — 100초 중 45초는 `ui_lint.sh` 한 곳이었다

> 측정일 2026-08-16 · 워크트리 `wt/smoke-timing-measure` · 포트 8091 ·
> 공용 dev DB(`vulnagent-db-dev`) · Windows 11 · git-bash(MSYS2) · bash 5.2
> 조치 대상은 `tests/ui_lint.sh` 하나다. **검사는 하나도 지우지 않았다**(217 통과 그대로).

## 요약 (결론 먼저)

1. **스모크 전체 102.7초 중 45.1초(43%)가 `tests/ui_lint.sh` 였다.** 서버도 DB 도 아니고,
   curl 을 한 번도 치지 않는 **정적 검사**가 최대 구간이었다.
2. 그 45초는 검사 내용이 아니라 **실행 방식**이었다. ① 항목마다 `grep` 프로세스를 새로
   띄웠고(총 700여 회 × fork 44~48ms) ② 참조 검사용 합본 1.9MB 를 임시 파일로 새로 만들어
   읽었는데 **갓 쓴 임시 파일의 첫 읽기가 9.7초**였다(백신 실시간 검사로 보인다).
3. 고친 뒤 **`ui_lint.sh` 35.6초 → 1.85초**, 스모크 전체 **102.7초 → 54.7초**(둘 다 3회 median,
   217 통과 0 실패로 동일). 검사 수·판정 논리·출력은 바이트 단위로 같다.
4. **나머지 구간은 손대지 않는다.** 2위 이하는 6~8초씩 고르게 흩어져 있고, 전부 "서버가
   실제로 그 일을 하는 시간"(수집 파이프라인·컨테이너 기동·DB 왕복)이라 줄이려면 검사를
   지우거나 위험을 지는 수밖에 없다. §5 에 하나씩 왜 안 하는지 적었다.

## 1. 측정 방법

### 1-1. 계측은 저장소에 남는다 (기본 꺼짐)

`tests/smoke.sh` 에 구간 계측을 심었다. **임시 코드가 아니다** — 다음에 또 재야 하므로 커밋에
남기되, 기본은 꺼져 있다.

```bash
VG_SMOKE_TIMING=1 ./tests/smoke.sh http://localhost:8091   # 켠다
./tests/smoke.sh http://localhost:8091                     # 기본 — 계측 없음
```

- 구간 경계는 소스의 `# --- 구간 ---` 주석 그대로다(+ 스크립트형 테스트 6개). `phase "이름"`
  한 줄이 앞 구간을 닫고 다음 구간을 연다. 구간별 **검사 수**는 `pass+fail+skip` 증가분으로 센다.
- **계측이 프로세스를 안 띄운다.** `date` 를 구간마다 부르면 fork 44~48ms 짜리 도구가 재려는
  대상을 오염시킨다(PR #587 에서 같은 함정을 겪었다). bash 5 의 `$EPOCHREALTIME` 과 정수
  산술만 쓰고, 명령치환(`$(...)`, 이것도 서브셸 fork)도 피해 전역 변수로 값을 넘긴다.
- 꺼져 있을 때 `phase()` 의 비용은 문자열 비교 1회다.

### 1-2. 측정 조건

- **3회 연속 실행의 median.** 1회는 파일 캐시 상태에 휘둘린다(실제로 같은 파이프라인이
  cold 9.3초 / warm 0.4초로 20배 차이가 났다 — §3).
- 공용 dev DB 는 다른 워크트리와 공유한다. 아래 표는 **다른 워크트리가 스모크를 돌리지 않는
  조용한 상태**의 값이다. 경합 중일 때의 값은 §4-2 에 따로 적었다.

## 3. 1위를 분해했다 — `ui_lint.sh` 45초의 실제 출처

`ui_lint.sh` 는 서버를 치지 않는다. 5개 검사 전부 파일을 읽고 문자열을 비교할 뿐이다.
검사별로 다시 쟀다(같은 방식의 `$EPOCHREALTIME` 마커).

| 검사 | 하는 일 | 조치 전 | 왜 |
|---|---|---:|---|
| 1 죽은 CSS 클래스 | PHP 의 클래스 125개가 app.css 에 있나 | ~6s | 클래스마다 `grep` 1회 = fork 125회 |
| 2 인라인 style | `style="…"` 금지(폭 계산 제외) | ~2.6s | 이미 1패스라 문제 없음 |
| 3 미정의 CSS 변수 | `var(--X)` 70개에 선언이 있나 | ~6s | 변수마다 `printf|grep` = fork 140회 |
| 4 조용히 잘리는 목록 | LIMIT 인데 페이저·OFFSET 없는 파일 | ~6s | 파일 45개 × grep 3회 = fork 135회 |
| 5 고아 CSS 클래스(경고) | app.css 클래스 363개가 코드에 쓰이나 | **~30s** | 아래 두 가지가 겹쳤다 |

### 5번이 30초였던 이유 둘

**① 클래스 363개마다 합본을 다시 훑었다.** fork 363회(≈16초)에 더해, 1.9MB 합본을 363번
재스캔해 총 700MB 가까이를 읽었다. git-bash 에서 fork 한 번이 44~48ms 라는 건 이 저장소가
이미 아는 사실이다(PR #587 이 `assert_*` 의 grep 102회를 걷어낸 것과 같은 자리).

**② 갓 만든 임시 파일의 첫 읽기가 9.7초였다.** 이건 예상 밖이라 따로 확인했다.

| 대상 | 첫 읽기 | 두 번째부터 |
|---|---:|---:|
| `find … -exec cat` 로 방금 만든 1.9MB 임시 파일 | **9.77s** | 0.30~0.43s |

같은 명령을 같은 파일에 다시 걸면 20배 이상 빨라진다. 스모크는 매번 임시 파일을 새로
만드므로 **항상 첫 읽기 값을 문다.** 원인은 백신 실시간 검사로 보인다(새로 쓰인 파일에
대한 on-write/on-first-read 스캔). 검증하지는 않았으므로 단정하지 않되, **대응은 원인과
무관하게 같다: 큰 임시 파일을 새로 만들지 않는다.**

### 고친 방식 — 판정은 그대로, 프로세스만 걷어냈다

- 1·3·4·5 를 **항목별 grep 루프 → 집합 차집합(`comm`)** 으로 바꿨다.
  동치인 근거: 원래 정규식들의 경계가 전부 `[^A-Za-z0-9_-]` (또는 `[^a-z0-9_-]`) 였다.
  즉 "그 문자집합으로 자른 **온전한 토큰**인가" 를 묻고 있었고, 토큰 집합을 한 번 뽑아
  차집합을 내는 것과 같은 판정이다.
- 4번은 파일마다 grep 3회 대신 **`grep -l` 3회로 전체 파일을 훑어** 목록 3개를 만들고
  `A - (B ∪ C)` 를 냈다. 파일별 판정 논리와 동일하다.
- 5번은 **합본을 아예 만들지 않는다.** 원본 파일들을 `awk` 한 번으로 훑어 토큰 집합만 뽑는다.
  원본은 앞 검사들이 이미 읽어 캐시가 더워져 있고, 출력도 35만 줄이 아니라 7천 줄이다.

### 같은 결과인지 어떻게 확인했나

- **정상 상태**: 옛 스크립트와 새 스크립트의 출력이 `diff` 로 **완전히 동일**(5 통과 0 실패).
- **위반 상태**: 5종 위반(죽은 클래스·인라인 style·미정의 CSS 변수·페이저 없는 LIMIT·고아
  클래스)을 심은 픽스처 트리에서도 **출력과 종료코드가 완전히 동일**(4 실패 + 경고 1).
  검사가 "통과만 빨라진" 게 아니라 **잡을 것을 그대로 잡는다**는 확인이다.

### 4-1. 조용한 상태(이 워크트리만 스모크를 돌릴 때) — 3회 median

조치 후 상위 구간(전체 53.554초):

|---:|---|---:|---:|---:|
| 1 | 컨테이너 드릴다운 + 컨테이너 SBOM | 7.939 | 14% | 60 |

1위였던 구간이 9위권으로 내려갔고, 상위 3구간이 전체의 38% 로 **평평해졌다** — 남은
시간은 특정 한 곳이 아니라 서버가 실제로 하는 일에 고르게 퍼져 있다.

### 4-2. 다른 워크트리가 동시에 스모크를 돌 때

절대값은 공용 DB 경합에 크게 흔들린다. 같은 코드로도 이만큼 벌어진다.

| 상태 | 조치 전 | 조치 후 |
|---|---:|---:|
| 조용함 | 102.7s | 54.7s |
| 다른 워크트리 1개가 동시 실행 | 134.6 / 142.7s | 86.3 / 93.9 / 97.1s |

`ui_lint.sh` 는 경합 상태에서도 45.9~54.9s → 2.9~3.3s 로 같은 비율만큼 줄었다.
**총시간을 절대값으로 비교할 때는 그때 다른 워크트리가 돌고 있었는지부터 확인해야 한다.**

경합 중 3회 중 1회는 32개 실패가 났다(`[ingest]` 응답 자체가 안 왔고 이후가 연쇄 실패).
알려진 공용 DB flaky 다 — 같은 조건에서 재실행하면 217 통과로 돌아왔고, 이번 변경은
정적 검사와 계측(기본 꺼짐)만 건드려 이 경로와 무관하다.

### 4-3. 계측을 켠 것이 더 느리지 않은가

같은 조건에서 연달아 재면 차이가 없다 — 켬 106.58s / 끔 106.86s(둘 다 217 통과 0 실패,
경합 중이라 절대값이 높다). 켜면 구간마다 정수 산술 2회와 배열 추가 1회가 늘 뿐이고
프로세스는 하나도 안 는다. 꺼져 있으면 `phase()` 는 문자열 비교 1회 후 즉시 반환한다.

## 5. 하지 않기로 한 것 — 그리고 그 이유

측정이 짚지 않은 곳은 건드리지 않았다. 후보로 검토했다가 **의도적으로 접은** 것들이다.

| 후보 | 왜 안 하나 |
|---|---|
| **단위테스트 27개(6.8s) 더 줄이기** | 이미 PR #581 이 `docker run` 27회(39초)를 **컨테이너 1회**로 묶었다. 남은 6.8초는 컨테이너 기동 1회 + PHP 27개 실제 실행이다. 더 줄이려면 테스트를 빼야 한다. |
| **go_buildinfo_host(6.7s) 제거** | 이건 유일하게 **진짜 Go 바이너리로 도는 e2e** 다. 고정 픽스처 테스트(go_deps_extract, 0.5s)가 대신하지 못한다. Go 툴체인이 없는 머신에서 SKIP 되는 처리(PR #590)도 그대로 둔다 — 회귀가 아닌 것에 빨간불이 켜지면 스모크를 못 믿게 된다. |
| **컨테이너 드릴다운(7.9s, 검사 60개) 축소** | 구간당 검사 수가 가장 많다(검사 1건당 132ms). 서버 왕복 자체이고, 줄이려면 검사를 지워야 한다. |
| **변경 추적(5.8s) 의 `docker exec` 10회 합치기** | 하나로 묶으면 빨라지긴 한다. 그러나 이 구간은 **ingest 전/후 상태를 각각 따로 읽어 비교**하는 것이 검사의 뼈대라, 묶는 순간 "언제 읽은 값인가" 가 흐려진다. 5.8초를 위해 검사의 의미를 흐릴 이유가 없다. |
| **구간 병렬화** | 이 스모크는 공용 dev DB 를 쓰고 이미 다른 워크트리와 경합한다(§4-2 의 flaky). 자기 자신을 병렬화하면 그 경합을 스스로 키운다. 앞 구간이 만든 상태를 뒤 구간이 assert 하는 순차 의존도 많다. |
| **rematch 검사 축소** | PR #226 이 이미 스캔 1건으로 줄여 뒀다. 이 블록의 의도는 "rematch 의 인증 방식" 이지 "DB 전체 재매칭 완주" 가 아니다. 더 줄이면 검사 의도가 깨진다. |
| **`assert_*` 추가 최적화** | PR #587 이 이미 grep 102회를 bash 내장 매칭으로 걷어냈다. 지금 남은 검사 구간들은 fork 가 아니라 **서버 응답 대기**가 지배적이다. |
| **고정 `sleep` 을 조건 대기로** | 찾아봤지만 **`sleep` 이 하나도 없었다.** 바꿀 게 없다. |

## 6. 남는 것

- 계측은 켜져 있지 않아도 코드에 남아 있다. 다음에 "스모크가 느리다" 는 말이 나오면
  `VG_SMOKE_TIMING=1` 로 **먼저 재고** 표를 붙인다.
- 이 저장소에서 배운 것이 하나 더 늘었다: **Windows 에서 큰 임시 파일을 새로 만들어 바로
  읽으면 첫 읽기에 초 단위를 문다.** 임시 합본을 만드는 대신 원본을 한 번 훑는 쪽이 낫다.
  (기존 교훈 — git-bash fork 44~48ms — 과 같은 계열이다.)
