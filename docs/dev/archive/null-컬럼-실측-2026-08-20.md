# 운영에서 항상 NULL 인 컬럼 15개 — 원인 분류 (2026-08-20)

> **이 문서는 삭제 결정이 아니라 분류다.** 컬럼·인덱스·테이블을 지우지 않았고 마이그레이션도 만들지 않았다.

"항상 NULL" 은 정반대의 두 가지를 뜻한다. **(A) 기능을 안 쓴다**(나중에 제거를 검토할 수 있다)와
**(B) 수집·저장 경로가 조용히 실패한다**(제거는 정확히 반대 방향이고 고쳐야 할 버그다). 가르지 않고
지우면 버그를 은폐한다. 이 문서는 15개 컬럼 각각이 둘 중 무엇인지를 **코드 근거로** 가른 기록이다.

- 분류 기준 — **(A)** 쓰는 코드는 살아 있는데 그 조작·기능을 아무도 쓴 적이 없다 / **(B)** 쓰는 코드가
  없거나 있어도 도달하지 못한다 / **(C)** 정상(그 상황이 안 일어났거나 원천에 값이 없거나 NULL 이
  기본값을 뜻한다) / **(D)** 판단 불가.
- **(A) 는 "제거해도 된다"는 뜻이 아니다.** 아래 (A) 로 분류한 것들은 전부 살아 있는 기능의 입력 칸이다.
- 운영 수치는 메인 세션이 조회한 2026-08-20 실측이고, 이 조사는 **운영 DB 에 접속하지 않았다**.
  재현은 공용 dev DB(`vulnagent-db-dev`) 읽기 전용 조회와 배포판 컨테이너로 했다.
- 감사 4컬럼과 0행 테이블은 애초에 대상에서 제외했다.

## 1. tb_container.sbom_format · sbom_hash — (A) 오프라인 SBOM 임포트 미사용

쓰는 쪽과 읽는 쪽이 **둘 다 있다.** 읽는 쪽은 호스트 상세의 컨테이너 개요(`server/src/container/overview.php:60-63`),
쓰는 쪽은 `server/src/ingest/store/containers.php:36`(INSERT 컬럼 목록)과 `:45`(`$f[13]`/`$f[14]`)다.

끊긴 곳은 그 **입력값**이다.

- 에이전트가 만드는 컨테이너 목록 한 줄은 `agent/vuln-inventory-agent.sh:1074` 이 찍는데,
  `%s` 13개 뒤에 `||` 가 붙어 **14·15번째 칸(= `$f[13]`·`$f[14]`)이 언제나 빈 문자열**이다.
  즉 에이전트는 이 두 값을 구조적으로 보내지 않는다.
- 이 두 칸을 채우는 유일한 코드는 서버 쪽 병합이다 — `server/public/ingest.php:177-179` 가
  업로드된 SBOM 문서의 `meta`(형식·sha256)를 같은 cid 의 컨테이너 행에 얹는다.
- 그 SBOM 문서는 관리자가 대상 서버의 `SBOM_DIR`(기본 `/opt/vuln-agent/sbom`, `agent/…:49`)에
  넣어야 생긴다. 디렉터리가 없으면 `collect_sbom` 은 즉시 반환한다(`agent/…:853-855`).

**판정 (A).** 경로 자체는 정상이고(2026-08-18 `#647` 로 호스트 SBOM 임포트까지 확장됐다), 운영에서
아무도 SBOM 파일을 넣지 않았을 뿐이다. 코드가 죽은 게 아니므로 제거 대상이 아니다.
codelore 에도 그 PR 의 제약이 남아 있다 — *"노드에 직접 넣어 수집시키는 것은 하지 않았다"*(github_pr#647).

확인 방법: 운영에서 SBOM 을 한 건이라도 넣었다면 ingest 응답의 `sbom_dropped` 나 웹 서버 로그의
`[ingest] SBOM …` 줄이 남는다(`server/public/ingest.php:186-191`).

### 부수 발견 — 문서·주석이 실제와 어긋난다 (F2)

- `agent/vuln-inventory-agent.sh:848-851` 주석은 파일명을 `<cid|name>.json` 이라고 안내하지만,
  서버는 **cid 키로만** 매칭한다(`ingest.php:178`, `server/src/ingest/sbom.php:205`).
  컨테이너 *이름*으로 파일명을 지으면 그 SBOM 은 통째로 버려진다.
- `docs/dev/데이터베이스.md:300`·`:314` 는 이 두 칸을 "에이전트가 함께 보낸 SBOM 메타 / 에이전트가
  안 보내면 NULL" 로 설명한다. 실제로는 **에이전트가 보낼 수 있는 칸이 아니다**(위 `:1074`).

## 2. tb_package.license 0.2% — (C) 설계대로. 단 pip 절반은 (B)

**분모가 오해를 만든다.** 라이선스 기능의 대상은 언어 생태계 8종뿐이고(`VG_LANG_MANAGERS`,
`server/src/license_summary.php:15`), OS 패키지(rpm/dpkg/apk)는 명시적으로 scope_out 이다
(`server/src/ingest/store/containers.php:58-59`). 112만 행의 대부분이 OS 패키지다.

`docs/dev/architecture.md:197` 이 소스를 못박아 두었다 — **SBOM · pip `METADATA` · composer
`installed.json` 세 곳뿐이고, npm/gem/maven/nuget/cargo 매니페스트는 파싱하지 않는다.**
에이전트에서 라이선스를 뱉는 지점도 정확히 둘이다(fd 3 으로 나가는 줄, 저장소 전체에서 이 둘뿐):

- `agent/vuln-inventory-agent.sh:1602` — pip `*.dist-info/METADATA`·`*.egg-info/PKG-INFO`
- `agent/vuln-inventory-agent.sh:1619` — composer `installed.json`

서버 쪽 경로(`server/src/ingest/packages.php:102-142` → `store/packages.php:35`)는 정상 동작한다.
dev DB 실측이 이를 뒷받침한다 — **composer 116행 중 116행에 라이선스가 있다(100%).**

| manager | 행수 | license 채움 | 해석 |
|---|---|---|---|
| composer | 116 | 116 | 파서·저장 경로 정상 |
| npm | 1,740 | 0 | 애초에 수집 안 함(설계) |
| rpm·apk·dpkg | 4,555 | 0 | scope_out(설계) |
| go·upstream | 888 | 0 | 수집 안 함(설계) |
| pip | 888 | 0 | dev 데이터는 픽스처라 근거가 안 된다 — `tests/sample-scan.json` 의 `langpkg` 에 `pkg_license` 섹션 자체가 없다 |

**판정 (C).** 0.2% 는 파서 실패가 아니라 **광고된 범위가 원래 좁아서**다.

### 부분 (B) — pip 라이선스의 절반이 사라진다 (F1)

`agent/…:1602` 은 `sed -n 's/^License: //p'` 로 **`License:` 헤더 하나만** 읽는다. 최신 파이썬
휠은 PEP 639 를 따라 `License-Expression:` 을 쓰거나 `Classifier: License :: …` 만 남긴다.

실측(`python:3.12-slim` + requests·jinja2·pyyaml·packaging·attrs·six 설치, dist-info 12개):

| 표기 | 개수 |
|---|---|
| `License:` (현재 파서가 읽는 것) | 6 / 12 |
| `License-Expression:` (안 읽음) | 5 / 12 |
| `Classifier: License ::` (안 읽음) | 6 / 12 |

개별로 보면 idna·urllib3·attrs·MarkupSafe·packaging 이 `License-Expression` 만 갖고 있어 통째로
누락되고, Jinja2 는 둘 다 없어 Classifier 로만 남는다. **pip 라이선스 커버리지가 절반쯤 깎인다.**
이 조사에서는 고치지 않는다(F1 로 넘긴다).

## 3. tb_host 등급 확정 5종 — (A) 확정을 아무도 한 적이 없다

확정 경로는 살아 있다. `server/src/assetgrade/confirm.php:53-60` 이 `criticality`·`grade`·
`grade_reason`·`approved_by`·`approved_at` 를 한 번에 쓰고, 호출부가 셋 있다 —
호스트 상세(`server/src/host/agent_control.php:67-82`), 자산 목록 일괄 확정
(`server/src/assets/confirm_post.php:34-35`), 등급 검토(`server/src/asset_grade_review.php:204`).

dev DB 에서 실제로 값이 들어간다:

```
호스트 76대 · grade 23 · grade_suggested 27 · criticality 0
```

**제안과 확정은 다른 칸이다.** 제안은 `server/src/assetgrade_history.php:111` 이 `grade_suggested`/
`grade_suggested_reason` 만 갱신하고 확정 칸을 절대 건드리지 않는다. 운영 조사 대상 목록에
`grade_suggested` 가 **없다** = 제안은 채워지고 있다는 뜻이다. 따라서 운영 상태는
**"제안은 도는데 사람이 확정을 한 번도 안 했다"** 이고, `criticality` 가 dev 에서도 0인 것으로 보아
확정 화면에서 중요도까지 함께 지정하는 흐름은 실사용에서 거의 안 쓰인다.

이건 설계된 상태다 — 등급 확정은 기관의 **법적 처분**이라 시스템이 대신할 수 없다
(`docs/dev/데이터베이스.md:140`). 값이 비어 있다고 컬럼을 지우면 확정 기능 자체가 사라진다.

## 4. tb_scan.cpe — 읽는 코드가 0개 (A) / 값 공백은 (C) 유력

수집·저장 경로는 첫 커밋부터 온전하다:
`agent/…:1763`(`. /etc/os-release; echo "${CPE_NAME:-}"`) → `:1773`(`put vuln_mapping cpe_name`)
→ `server/public/ingest.php:65` → `server/src/ingest/store/scan.php:80`.

**그런데 저장소 어디에서도 이 컬럼을 읽지 않는다.** `store/scan.php` 의 INSERT 를 제외하면
`server/` 전체에 `cpe` 참조가 없다.

값이 비는 이유는 원천에 필드가 없어서일 가능성이 크다. 배포판별 실측:

| 이미지 | `CPE_NAME` |
|---|---|
| `debian:12` | 없음 |
| `ubuntu:24.04` | 없음 |
| `alpine:3.20` | 없음 |
| `rockylinux:9` | `cpe:/o:rocky:rocky:9::baseos` |

dev DB 에서는 rocky 449건 전부에 cpe 가 채워져 있다(debian·amzn 24건씩은 픽스처가 넣은 합성값이라
근거에서 뺀다). 즉 **RHEL 계열이면 채워지고 Debian·Ubuntu 계열이면 안 채워진다.**

**확정에 필요한 것은 운영 쿼리 한 줄이다**(이 조사는 운영 DB 미접속):

```sql
SELECT os_id, COUNT(*) n, SUM(cpe IS NOT NULL) has_cpe FROM tb_scan GROUP BY os_id;
```

- Debian/Ubuntu 계열이면 → **(C) 정상**, 문서 설명(`데이터베이스.md:240`: "NULL = 배포판이 안 주는 경우")과 일치.
- rocky/rhel 계열인데 NULL 이면 → **(B)** 이고 `agent/…:1763` 을 봐야 한다.

읽는 쪽이 없다는 사실만은 확정이라 분류는 **(A)** 로 둔다. 다만 CPE 는 향후 CPE 기반 매칭에 쓸 여지가
있는 값이라 제거 판단은 이 문서 밖의 결정이다.

## 5. tb_host_account.pw_inactive_days — (C) 원천이 비어 있다

경로는 정상이다. 에이전트가 `/etc/shadow` 를 awk 로 8칸(name·lastchg·min·max·warn·inactive·expire·lock)
탭 구분으로 보내고(`agent/…:2207`), 서버가 같은 순서로 분해해 저장한다
(`server/src/account_inventory.php:161-175`, INSERT 는 `:228`·`:241`).

`debian:12` 컨테이너에서 에이전트와 **똑같은 awk** 를 돌린 결과(`^I` 는 탭):

```
root^I20668^I0^I99999^I7^I^I^I1
daemon^I20668^I0^I99999^I7^I^I^I1
```

inactive(6번째 칸)와 expire(7번째 칸)가 **기본값으로 비어 있다.** `chage -I` 를 걸지 않으면
그대로다 — 리눅스 기본 상태다.

**결정적 근거는 이웃 칸이다.** 같은 줄의 **바로 다음 칸**인 `expire_date` 가 운영에서 54건 채워져
있다. 분해가 인덱스 6까지 도달했다는 뜻이므로, 인덱스 5(`pw_inactive_days`)를 못 읽는 자리밀림도
`/etc/shadow` 미수집(비-root 실행)도 **아니다.** 값이 진짜로 없는 것이다.

같은 이유로 `expire_date` 54/4,568 도 **(C)** 다 — 만료일을 실제로 건 계정만 채워진다.

### 부수 발견 — 문서 설명이 과하게 넓다 (F3)

`docs/dev/데이터베이스.md:378` 은 "`is_locked`/`pw_*`/`expire_date` 가 NULL 이면 비-root 실행이라
`/etc/shadow` 를 못 읽은 것" 이라고 일괄 설명한다. `pw_inactive_days` 는 **root 로 잘 읽고도 비는 것이
정상**이라 이 설명이 그대로 적용되지 않는다(위 54건이 반증이다).

## 6. 나머지 6개 — 대부분 (C), 표본이 한 자리다

아래 컬럼은 전부 쓰는 코드가 살아 있고, 지금까지 그 상황이 안 일어났을 뿐이다.
**행수가 1~26행이라 통계적 근거로는 약하다** — "항상 NULL" 이라는 말이 무색한 표본이다.
