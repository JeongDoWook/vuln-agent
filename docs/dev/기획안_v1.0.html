01

왜 이 주제인가

개발 배경 및 목적

오픈소스 의존성이 폭증하면서, 내 PC·서버에 깔린 소프트웨어에 어떤 알려진 취약점(CVE)이 숨어 있는지 개인·중소기업이 파악하기 어렵다.

기존 스캐너를 돌리면 문제가 하나 더 생긴다. 취약점이 수백 개씩 쏟아지는데 그중 상당수가 오탐이다. 담당자는 "이건 진짜인가, 이미 고쳐진 건가"를 손으로 걸러야 하고, 경고가 너무 많아 결국 아무도 안 보게 된다.

그래서 필요한 건 "더 많은 경고"가 아니라 믿을 수 있는 소수의 판단이다. 이 판단·조치 과정을 에이전트가 자율적으로 수행하고, 그 근거를 화면에 남기게 하는 것이 목표다.

02

핵심 전략

매칭은 검증된 도구에, 차별점은 그 위 레이어에
피해야 할 함정 "백포트·오탐을 잘 잡는 매칭을 직접 만들어 차별화"는 위험하다. Trivy·Grype·OpenSCAP는 이미 각 배포판 보안 피드(Red Hat OVAL, Ubuntu USN, Debian Tracker)로 백포트를 인식해 오탐을 억제한다. 이건 성숙한 도구의 기본기이지 신선한 기능이 아니며, 직접 만들면 오히려 오탐이 더 많을 수 있다.
결정 (구현 결과) OS 패키지 취약점 매칭은 OSV.dev API 를 직접 조회해 검증된 공개 데이터에서 그 정확도를 상속받는다 — 당초 검토했던 Trivy·Grype 같은 스캐너 바이너리 호출 대신, API 직접 조회가 Docker 배포 구조에 더 단순했다(KISS). 오탐 억제는 OSV 버전필터 + 패키지 changelog 대조로 직접 구현해, 우리의 기여를 그 위 레이어(런타임 노출 상관·백포트 근거·KEV/EPSS 우선순위)에 둔다.

// 진짜 차별점 (강한 순서)

①
런타임 노출 상관 최우선
기존 스캐너는 아티팩트만 본다. 우리 에이전트는 열린 포트·실행 서비스·프로세스를 이미 수집한다. "openssl이 취약하다"가 아니라 "그걸 쓰는 nginx가 443으로 외부에 떠 있다"까지 말해 우선순위를 가른다. 추가 개발 거의 없음.
②
EPSS + CISA KEV 결합
점수 나열 대신 실제 악용 확률(EPSS) + 실제 악용된 목록(KEV)을 결합한다. "CVSS 9.8이나 악용확률 0.1%" vs "CVSS 6.5이나 현재 공격 중"을 구분. 둘 다 무료.
③
설명가능한 오탐 억제(백포트)
오탐을 숨기지 않고 왜 안전한지 근거를 제시한다. OSV 버전필터로 1차로 거르고, 통과한 건도 패키지 changelog 의 CVE 수정 기록이 있으면 tb_suppressed_finding 으로 분리한다 — 위험 집계는 그대로 두고 오탐만 빠지며, 억제 근거는 호스트 상세 화면에 그대로 노출된다.
④
경량 상주 에이전트 + 시계열
CI/1회성이 아니라 호스트별 주기의 상주 수집(systemd 서비스, 기본 60분). "어제 안전 → 오늘 신규 CVE로 취약"을 스캔 대조로 추적하고 여러 서버를 한눈에 본다. 에이전트 자원은 실행별 프로세스 트리 기준으로 계측한다.
⑤
KISA 국내 연동
해외 도구가 하지 않는 국내 보안공지 매칭. 보호나라 공식 RSS 3종을 수집하고 신규 공지는 상세 본문까지 저장해 그대로 보여준다. 신선함 + 사회적 기여 포인트.

05

최적화

서버에 무리 안 가고, 대규모에서도 안 터지게
피드 스케줄러 사이드카
CVE 피드 5종을 중앙이 로컬 DB(tb_cve 등)로 당겨와 보관. 매칭은 로컬끼리 → 빠르고, 대상 서버 에이전트는 CVE 소스에 직접 접속할 필요 없음. 스케줄러가 1분마다 due 커넥터만 실행하고 수집 후 전체 스캔을 재매칭한다.
백포트 억제 2단계
OSV 버전필터로 먼저 걸러내고, 그걸 통과한 소수 건만 changelog 대조(가장 무거운 단계)로 넘긴다 → 불필요한 changelog 파싱을 줄인다. 수집 단계에서 --no-changelog로도 끌 수 있다.
무중단 배포
운영은 ../server를 읽기전용 마운트. PHP 만 바뀌면 git pull 한 줄로 반영(opcache 가 2초 내 갱신), Dockerfile·compose·caddy 변경 시에만 재빌드.
스키마 마이그레이션 자동화
db/migrations/NNNN_*.sql 중 미적용분만 번호순 자동 적용 → 스키마 변경이 파일 하나 추가로 끝난다.
에이전트 자원
nice 19 / ionice idle 최저 우선순위 + 명령별 타임아웃. 실행별 프로세스 트리의 피크 RSS와 CPU 시간을 호스트 용량 대비 비율로 기록한다.
간소화 결정 (YAGNI) 당초 검토했던 델타 수집·증분 매칭·조회 시점 매칭은 만들지 않았다. 매 수집 전량 전송 + ingest 시 매칭(및 피드 수집 후 전체 재매칭)만으로도 충분히 단순하고 빨라 실제 병목이 되지 않았다.

개발 순서

전부 다 하되, 항상 "돌아가는 상태"를 유지하며 쌓았다 — 완료 현황
1뼈대 · 수집 & 판단
완료
  • 패키지(NEVRA·소스패키지·벤더) + 런타임(리스닝 포트·실행 프로세스) 수집
  • OSV.dev API 직접 조회로 CVE 매칭(스캐너 도구 호출 대신 API 직접 조회로 단순화)
  • 런타임 노출 + EPSS/KEV로 우선순위 매겨 웹 대시보드에 표시
→ 완료. 에이전트가 호스트별 설정 주기로 수집하고 중앙이 판단해 근거와 함께 웹에 보여준다.
2국내 특화 · 차별화 무기
완료
  • KISA 보호나라 공식 RSS 3종으로 국내 보안공지 수집 (크롤링보다 안전)
  • NVD/OSV 결과와 매칭해 공지의 CVE 연결, 신규 공지는 상세 본문까지 수집
→ 완료. 국내 특화 = 신선함 + 사회적 기여 포인트 확보(국내공지 목록·상세 페이지).
3조치 · 야심 파트
부분 완료
  • 취약점별 조치안(OSV 의 fixed_version 기준 업그레이드 버전) 표시 — 완료
  • 의존성 충돌 시뮬레이션 자기검증 — 만들지 않기로 결정(YAGNI, 정적 조치안 제시로 충분)
→ 조치안 제시까지 완료. 자기검증 루프는 범위에서 제외했다.
4당초 계획에 없던 추가 구현
완료
  • 백포트 오탐 억제(changelog 근거) · 보안설정 점검(CCE) · 변화 추적
  • 자산 관리 + 설정형 RBAC(역할×메뉴 권한) · 감사로그 + 소프트삭제
  • Export API(JSON/XML) + API 토큰 발급 · HTTPS 배포(Caddy) · 스키마 마이그레이션 자동화
→ 매칭 정확도로 경쟁하지 않기로 한 대신, 이 위 레이어를 계획보다 두껍게 쌓았다.
핵심 전략 한꺼번에 병렬로 만들면 터진다. 순서대로 쌓아 각 단계가 끝날 때마다 돌아가는 상태를 유지했고, 그 결과 1~2단계뿐 아니라 3단계 상당 부분과 계획에 없던 기능까지 확보했다.
07

KISA 데이터 연동

크롤링보다 RSS 우선

KISA는 공식 API를 주지 않지만, 보호나라가 공식 RSS 서비스(보안공지·공지사항)를 제공한다. 이 편이 크롤링보다 훨씬 유리하다.

  • 1순위 · RSS — 공식 제공이라 이용약관 리스크 없음, HTML 파싱 깨질 걱정 없음, 보고서에 "KISA 공식 RSS 활용"으로 당당히 기재.
  • 2순위 · 공지 페이지 파싱 — RSS에 없는 상세만 보완적으로. robots.txt·이용약관 확인, 과도한 요청 자제.
  • 출처 명시(필수) — 규정 제8조 5·6항. "KISA 보호나라 공개 데이터" 출처를 결과보고서에 명확히 기재.
구현 결과 3종 RSS 를 스케줄러가 주기 수집하고, 신규 공지는 상세 본문까지 저장해 /advisory.php 에서 그대로 보여준다. RSS 는 피드당 최신 10건만 주므로 과거 이력은 1회성 백필 스크립트(bin/backfill_kisa.php·backfill_kisa_content.php)로 채웠다.
08

AI 모델 활용 방식

운영규정 제9조 대응
최종 결정 (구현 결과) 1~3단계(수집·매칭·판단·조치안 표시)는 전부 규칙/DB 조회로 처리되며 AI 모델이 전혀 필요 없다. 조치안도 OSV 의 fixed_version 을 그대로 보여주는 구조적 표시일 뿐, 자연어 생성이 아니다.

AI 리포트 생성 본체에서 제외

당초 검토했던 로컬 오픈웨이트 모델(LLaMA·Gemma·Qwen) 기반 자연어 리포트 생성기는 만들지 않았다. 대신 GET /export.php(JSON/XML)로 스캔 결과를 내보내, 필요하면 외부 시스템이 가져가 자체적으로 리포트를 만들도록 경계를 나눴다 — 본체가 AI 런타임에 묶이지 않는다.

보조 도구 문제 없음

코드 작성·디버깅에 Claude·GPT 활용은 규정상 자유. 결과보고서 [붙임2] 4번에 활용 범위 한 줄 기재로 끝. (동작 원리 이해는 필수 — 미흡 시 감점)

결과 규정 리스크를 원천 차단하는 가장 보수적인 선택 — 판단·조치 로직에 AI 모델을 아예 넣지 않았다. AI 는 코드 작성 보조로만 썼고, 그 사실을 결과보고서에 기재한다.

확정된 것

개발을 마친 지금 시점 — 당초 기획 대비 달라진 점
  1. 스택 확정 — Bash 수집 에이전트 + PHP/MySQL 중앙 서버(Docker). 당초 검토했던 Python 은 채택하지 않았다.
  2. 매칭 방식 확정 — Trivy/Grype 같은 스캐너 도구 호출 대신 OSV.dev API 를 직접 조회하는 방식으로 단순화(KISS).
  3. AI 활용 범위 확정 — 판단·조치 로직엔 AI 모델을 넣지 않고 코드 작성 보조로만 사용. 리포트 생성은 Export API 로 경계 밖으로 분리.
  4. 배포 확정 — Docker Compose(dev/prod) + Caddy(HTTPS) + agent/install-agent.sh(systemd 상시 poll 서비스, 호스트별 수집 주기, cron 폴백).
