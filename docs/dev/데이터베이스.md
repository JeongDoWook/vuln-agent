# 데이터베이스 — 테이블 레퍼런스

> 스키마 기준: 2026-08-09 · 운영 51개 테이블(`tb_schema_migrations` 포함).

MySQL 8. 전 테이블 `tb_` 접두사 + 감사 4컬럼(`created_at`·`updated_at`·`is_deleted`·`deleted_at`) 통일.
소프트삭제는 `is_deleted=1`(물리 삭제 안 함). 스키마 변경은 `db/migrations/`(타임스탬프 파일명, 멱등),
`deploy/migrate.sh` 가 미적용분만 적용하고 `tb_schema_migrations` 에 기록한다.

- **관계도(ERD)** 는 `architecture.md §5` 에 있다 — 여기는 **테이블별 컬럼·책임** 레퍼런스다.
- 현재 51개 테이블(`tb_schema_migrations` 포함). PK 는 `[PRI]`, 유니크 `[UNI]`, 인덱스 `[MUL]` 로 표기.

## 명명규칙 — 테이블은 단수, PK 는 `<테이블명(tb_ 제외)>_id`

**이전 규칙은 "PK 는 전부 `id`" 였다. 지금은 아니다.** 옛 규칙에선 PK 가 `id` 인데 그걸 가리키는
FK 는 `host_id`·`scan_id`·`container_id` 라, 같은 값인데 조인 양쪽 이름이 달랐다. 새 규칙은
**부모 PK 이름 = 자식 FK 이름**이 되게 맞춘 것이다.

```sql
-- 옛 규칙 (PK=id, FK=host_id — 같은 값인데 이름이 다르다. 테이블명도 복수형이었다)
FROM tb_scan s JOIN tb_host h ON h.id = s.host_id

-- 새 규칙 (이름이 같아 눈으로 바로 읽힌다)
FROM tb_scan s JOIN tb_host h ON h.host_id = s.host_id
```

1. **테이블명은 단수** — 복수형이던 이름은 전부 단수로 바꿨다(`tb_host`·`tb_finding`·`tb_package`…).
2. **대리키 PK 는 `<단수 테이블명>_id`** — `tb_host.host_id`, `tb_feed_connector.feed_connector_id`.
   더 이상 `id` 라는 컬럼은 만들지 않는다.
3. **FK 는 부모 PK 이름을 그대로 쓴다** — `tb_feed_collection_log.feed_connector_id`,
   `tb_agent_replay_nonce.agent_token_id`. 역할을 구분해야 하는 경우만 접두어를 붙인다
   (예: 동일 부모를 역할별로 두 번 참조하는 경우).
4. **인덱스·제약 이름(`idx_hosts_is_deleted`·`fk_scans_host`·`uq_find` 등)은 바꾸지 않는다.**
   컬럼 rename 은 메타데이터 전용이라 즉시 끝나지만 인덱스 rename 은 재구축 비용이 든다
   (920만 행 `tb_cve_affected_package`).

### 규칙을 적용하지 않는 예외 (의도적 — 빠뜨린 게 아니다)

아래 테이블은 **일부러 `<테이블명>_id` PK 를 두지 않는다.** 규칙대로 대리키를 새로 만들면
스키마가 오히려 나빠진다. 다음 사람이 "누락"으로 오해해 또 바꾸지 않도록 여기 명시한다.

| 테이블 | PK | 그대로 두는 이유 |
|---|---|---|
| `tb_cve` | `cve_id` | CVE 번호 자체가 자연키. 이미 규칙과 정합 |
| `tb_kev_catalog` | `cve_id` | FK-as-PK(`tb_cve` 1:1 확장). `kev_catalog_id` 대리키 신설은 YAGNI |
| `tb_kernel_cve` | `cve_id` | 동일하게 FK-as-PK |
| `tb_finding_evidence` | `finding_id` | `tb_finding` 1:1 확장의 FK-as-PK |
| `tb_package_summary` | `(package_name, ecosystem)` | 복합 자연키. 사전집계 테이블에 대리키 불필요 |
| `tb_kernel_cve_fix` | `(cve_id, stream)` | 복합 자연키 |
| `tb_agent_replay_nonce` | `(agent_token_id, nonce_hash)` | 복합 자연키(재전송 방지 nonce) |
| `tb_collection_stage` | `(scan_id, stage_code)` | 복합 자연키 |
| `tb_schema_migrations` | `filename` | 마이그레이션 러너 자신의 인프라 테이블. **PK 를 바꾸면 `deploy/migrate.sh` 가 자기 이력을 못 찾아 전체 마이그레이션이 재실행된다.** 테이블명 단수화도 하지 않는다 |

테이블명이 이미 단수/불가산이라 **PK 만 바뀐** 것들도 있다(`tb_activity_log` → `activity_log_id`,
`tb_applied_errata` → `applied_errata_id`, `tb_debsecan`·`tb_debian_tracker`·`tb_ubuntu_oval`·
`tb_vendor_errata`·`tb_vendor_unfixed` 동일).

> **HTTP 인터페이스는 별개 레이어다.** `host.php?id=3` 같은 URL 파라미터는 그대로 둔다 —
> 저장된 북마크·감사로그에 남은 URL 이 깨지기 때문. DB 명명규칙이 URL 을 따라오지 않는다.

## 1. 수집·인벤토리 — 에이전트가 보내온 원본

### tb_host — 모니터링 대상 서버
`host_id [PRI]`, `fqdn [UNI]`, `hostname`, `os_id`, `os_version`,
`criticality`, `grade [MUL]`, `grade_reason`, `approved_by [FK SET NULL]`, `approved_at`,
`grade_suggested`, `grade_suggested_reason`, `agent_speed_tier`,
`first_seen`, `last_seen`, `last_seen_ip`, `poll_schedule_seconds`
- 호스트 1행. `fqdn` 이 자연키(유니크). 스캔이 쌓여도 호스트는 하나.
- `last_seen_ip` 는 에이전트 요청의 실제 원격 주소를 저장한다. 컨테이너가 보고한 내부 주소를 자산 IP 로 오인하지 않는다.
- `poll_schedule_seconds` 는 호스트별 정기 수집 주기의 SSOT다. 연결 지연 판정도 고정 1시간이 아니라 이 주기를 기준으로 한다.
- **자산 중요도·보안등급(ISMS-P 1.2.1)** — `criticality` 는 `ENUM('HIGH','MEDIUM','LOW')`(화면 라벨 상/중/하는 `VG_ASSET_CRITICALITY`), `grade` 는 N2SF 등급 `C`(기밀)/`S`(민감)/`O`(공개) 한 글자다.
- **"판정은 사람이, 초안은 시스템이" — 컬럼이 둘로 나뉜 이유.** 등급 판정 기준은 「정보공개법」 제9조 비공개 대상정보의 호 매핑이고 업무정보 등급 확정은 기관의 **법적 처분**이라 시스템이 대신할 수 없다. 그래서 사람이 확정한 값(`grade`·`grade_reason`·`approved_by`·`approved_at`)과 시스템 초안 제안(`grade_suggested`·`grade_suggested_reason`)을 **다른 칸에** 담는다. `src/assetgrade.php` 의 제안 함수는 `grade` 를 절대 쓰지 않고, 화면도 제안값엔 '제안' 표기를 붙인다. 같은 칸에 쓰면 "시스템이 등급을 정했다"가 되어 이 경계가 무너진다.
- `approved_by` 는 `tb_user(user_id)` FK **ON DELETE SET NULL** — 사용자를 지워도 승인 이력만 끊고 등급은 남긴다. 목록 등급 필터용 인덱스는 `idx_host_grade (is_deleted, grade)`(화면이 늘 `is_deleted = 0` 을 함께 걸므로 그 순서).
- `agent_speed_tier`: `ENUM('very_fast','fast','normal','slow')` NOT NULL DEFAULT `'normal'`. 호스트별로 에이전트의 CPU 제한·JSON 조립 타임아웃·메모리 상한을 중앙에서 정한다(SBC 와 데스크톱의 사양 차이). 4단계 → 값 매핑(`cpu_quota_percent`·`packaging_timeout_seconds`·`mem_max_mb`)의 유일한 정의처는 `VG_AGENT_SPEED_TIER_MAP`(`src/agentspeedtier.php`) — 고정 4종이라 하드코딩이 맞고, `agent-poll.php`·`agentcommand.php`·`host.php` 가 모두 이 파일 하나만 본다.

### tb_scan — 수집 1회분(시계열의 단위)
`scan_id [PRI]`, `host_id [FK]`, `collected_at`, `agent_version`, `schedule`, `elapsed_seconds`, `peak_rss_mb`, `cpu_seconds`,
`os_id`, `os_version`, `kernel`, `running_kernel`, `kernel_latest`, `kernel_reboot_needed`, `cpe`,
`package_family`, `content_hash`, `package_count`, `exposure_count`, `raw_json`, `received_at`
- 한 호스트의 매 수집이 1행. 이 밑으로 package/exposure/process/finding 이 매달린다.
- `content_hash`: 내용이 바뀔 때만 새 스냅샷을 만드는 기준(PID 등 잡음 제외). 같은 내용 재전송은 새 행을 안 만든다.
- **os_id/kernel 등은 수집 시점 스냅샷** — 호스트의 현재값을 복제한 게 아니라 "그때 그랬다"는 시점 사실이라 정규화 대상 아님.
- `kernel_reboot_needed`: 커널 패치됐지만 옛 커널 실행 중 → 재부팅 필요 판정(매처가 씀).
- `schedule`: 에이전트의 수집 주기 문자열(예 `hourly`/`daily`/`*:0/30`). 에이전트가 `meta.schedule` 로 실어 보내면 최신 스캔에 기록한다. 상시 데몬 노드는 실제 SSOT가 `tb_host.poll_schedule_seconds`(호스트 상세에서 조회·변경)이고, `tb_scan.schedule`은 그 시점 실행 주기의 스냅샷이다.

### tb_package — 설치 패키지
`package_id [PRI]`, `scan_id [FK]`, `container_id`, `manager`, `name [MUL]`, `version`, `arch`,
`source_pkg [MUL]`, `source_version`, `origin`, `vendor`, `license`
- `container_id`: 0=호스트, 양수=그 컨테이너 내부 패키지.
- `source_pkg`/`source_version`: 백포트·오탐 감소의 핵심(바이너리 아닌 소스패키지 단위 매칭).
- `origin`: 서드파티 저장소 판정(오억제 방지).
- `license`: SPDX 식별자(또는 자유서술 표기) 원문. SBOM(CycloneDX/SPDX)·pip METADATA·composer
  installed.json 경로로만 채워진다 — rpm/apk 목록·rpmdb 나 다른 언어 매니페스트 직접 파싱으로는
  채우지 않는다(비면 NULL). 분류는 `vg_license_classify()`(`src/license_risk.php`)가 요청 시점에
  순수함수로 계산하고, 목록·KPI 는 `tb_package_license_summary` 사전집계만 읽는다(idx_package_manager_name 인덱스로 목록 필터링).

### tb_exposure — 리스닝 소켓(포트) = 런타임 노출
`exposure_id [PRI]`, `scan_id [FK]`, `container_id`, `pid`, `proc`, `proto`, `bind_addr`, `port`,
`scope [MUL]`, `exe_pkg [MUL]`, `loaded_pkgs`
- 차별점 ①(런타임 노출 상관)의 원천. `scope` = EXTERNAL/LOCAL/BOUND/FILTERED.
- `loaded_pkgs`: 그 프로세스가 로드한 패키지들의 **CSV** — 원본 수집 신호라 정규화하지 않는다(쪼개도 이득 없음).

### tb_process — 실행 프로세스(포트 없어도)
`process_id [PRI]`, `scan_id [FK]`, `container_id`, `pid`, `comm`, `username`, `exe_pkg [MUL]`, `loaded_pkgs`
- "실행중/사용중"까지 잡아 상태를 정밀 구분(설치만 vs 로드 vs 실행 vs 노출). `loaded_pkgs` 는 `tb_exposure` 와 동일하게 CSV 신호.

### tb_container — 컨테이너 인벤토리
`container_id [PRI]`, `scan_id [FK]`, `cid`, `name`, `image`, `os_id`, `os_version`, `manager`, `pkg_count`
- 컨테이너별 메타. 컨테이너 내부 패키지·프로세스·노출은 각 테이블의 `container_id` 로 연결(호스트 신호가 컨테이너로 새지 않게 격리).
- PK 를 `container_id` 로 맞추면서 `tb_package`·`tb_finding`·`tb_suppressed_finding` 이 이미 쓰던 FK 이름과 **정확히 일치**하게 됐다 — 이 명명규칙 통일의 이득이 가장 큰 지점.

### tb_collection_stage — 수집 단계별 완전성
`scan_id [PRI][FK CASCADE]`, `stage_code [PRI]`, `status`, `item_count`, `created_at`
- 스캔 1회의 **각 수집 단계가 실제로 돌았는지**를 남긴다. 에이전트가 한 단계를 통째로 못 돌면(권한 부족·바이너리 없음) 그 영역이 조용히 0건이 되는데, 이게 "취약점 없음"으로 보이면 미탐이다 — 단계 상태를 따로 기록해 호스트 상세에 **경고로 드러낸다**.
- `stage_code` 5종: `packages`·`language_packages`·`runtime_processes`·`network_exposure`·`containers`. 한글 라벨은 `VG_COLLECTION_STAGE_LABEL`(`src/format.php`) — 고정된 알려진 구조라 하드코딩이고, 새 단계는 생산자와 함께 한 줄 늘린다.
- `status`: `MISSING`(단계가 아예 안 돌았다) / `EMPTY`(돌았는데 결과가 0건 — 정상일 수 있다). 이 둘을 구분하는 게 이 테이블의 존재 이유다.
- 쓰기는 `ingest_store.php` 가 `ON DUPLICATE KEY UPDATE` 로 멱등 upsert — **동일 스냅샷 재전송이어도** 완전성만은 최신으로 갱신한다(스캔 행은 안 늘리면서 수집기 상태는 최신을 보여주려고).
- 복합 자연키 PK 라 명명규칙 **예외**. 감사 4컬럼 없음(`created_at` 만) — 스캔에 CASCADE 로 매달린 파생 기록이라 소프트삭제 대상이 아니다.

### tb_scan_run — 실제 수집 실행 이력
`scan_run_id [PRI]`, `host_id [FK CASCADE]`, `scan_id [FK CASCADE]`, `collected_at`, `received_at`, `content_changed`,
`package_count`, `exposure_count`, `agent_version`, `schedule`, `elapsed_seconds`, `peak_rss_mb`, `cpu_seconds`, `mem_total_mb`, `cpu_cores`
- 에이전트가 실제로 완료한 **매 실행을 1행씩** 남긴다. 내용이 같아 `tb_scan` 스냅샷을 재사용해도 실행 이력은 누적된다.
- `content_changed` 는 이번 실행이 새 `tb_scan` 스냅샷을 만들었는지 표시한다.
- 메모리·CPU 지표는 서버 전체 사용량이 아니라 에이전트 프로세스 트리의 피크 RSS와 CPU 시간이다. 화면의 백분율은 각각 `mem_total_mb`, `cpu_cores × elapsed_seconds`를 분모로 계산한다.

### tb_agent_command — 에이전트 명령 큐와 진행상태
`agent_command_id [PRI]`, `host_id [FK]`, `run_at`, `status`, `progress_percent`, `progress_stage`, `progress_message`,
`created_by`, `started_at`, `heartbeat_at`, `cancel_requested_at`, `cancelled_at`, `executed_at`, 감사 4컬럼
- 웹의 즉시 실행·예약 실행을 중앙 큐에 저장하고, 에이전트가 10초 poll로 가져간다. 중앙에서 대상 서버로 인바운드 접속하지 않는다.
- 실행 중에는 진행률·단계·설명과 heartbeat를 갱신한다. 중단 버튼은 `cancel_requested_at`을 기록하고 에이전트가 다음 poll/단계 경계에서 종료한 뒤 `cancelled_at`을 남긴다.
- `run_at IS NULL`은 즉시, 값이 있으면 예약 명령이다. 완료·실패·취소 이력은 소프트 삭제 정책으로 보존한다.

### tb_host_account — 계정 인벤토리
`host_account_id [PRI]`, `host_id [FK CASCADE]`, `scan_id [FK CASCADE]`, `username`, `uid`, `gid`, `shell`, `home`,
`is_locked`, `is_sudoer`, `is_system`, `pw_last_change`, `pw_min_days`, `pw_max_days`, `pw_warn_days`,
`pw_inactive_days`, `expire_date`, `last_login_at`, `never_logged_in`, `collected_at`, `received_at`, 감사 4컬럼
- 호스트의 **실제 계정 목록**을 스캔별로 보관한다. 지금까지는 계정 "설정 정책"(login.defs·PAM·sshd)만 봤고 계정 자체는 안 봐서 ISMS-P 2.5.1·2.5.2·2.5.5·2.5.6 과 N2SF AC 계정관리가 통째로 공백이었다 — 그 근거 데이터다.
- **UNIQUE(scan_id, username)** — 스캔 1회분 안에서 계정명은 유일하다. `scan_id` 를 남겨 두면 나중에 스냅샷 diff(전회 대비 계정 증감)가 가능하다.
- **패스워드 해시는 저장하지 않는다.** 에이전트도 보내지 않는다(정책 필드와 잠금 여부만).
- **NULL 은 "없음"이 아니라 "판정 불가(NA)"다.** `is_locked`/`pw_*`/`expire_date` 가 NULL 이면 비-root 실행이라 `/etc/shadow` 를 못 읽은 것이고, `is_sudoer` NULL 은 sudoers·sudo 그룹 미수집, `never_logged_in` NULL 은 lastlog 미수집이다. 판정 로직은 `src/account_inventory.php`(`VG_ACCOUNT_STALE_LOGIN_DAYS`=90일 미로그인, `VG_ACCOUNT_SYSTEM_UID_MAX`=999).
- `collected_at` 은 에이전트가 신고한 수집 시각, `received_at` 은 중앙이 실제로 받은 시각이다(자기신고값과 서버 사실을 섞지 않는다).

### tb_package_dependency — 패키지 의존성 그래프
`package_dependency_id [PRI]`, `scan_id [FK CASCADE]`, `container_id`, `source`, `parent_manager`, `parent_name`,
`parent_version`, `child_manager`, `child_name`, `child_version`, `created_at`, `edge_hash [생성컬럼]`
- 부모→자식 의존성 엣지. `source='sbom'` 은 SBOM(CycloneDX) `dependencies`, `source='pom'` 은 pom.xml 최상위 `<dependencies>` 의 best-effort 직접 선언이다. 둘 다 있으면 SBOM 을 우선한다(애플리케이션 로직).
- `source='sbom'` + parent 전부 NULL = 그 SBOM 의 **루트(최상위 프로젝트) 표식행**. 루트 자신을 parent 로 갖는 엣지의 child 가 직접 의존성이다. `source='pom'` 은 parent 가 항상 NULL.
- `container_id`: 0=호스트 자신, 양수=그 컨테이너(`tb_package` 관례와 동일).
- **UNIQUE(scan_id, container_id, edge_hash)** — 원래는 9개 컬럼 복합키였는데 utf8mb4 에서 약 4,200바이트가 되어 InnoDB 인덱스 상한 3,072바이트를 넘었다(운영 `ERROR 1071`). `edge_hash` 는 `source`+parent 3필드+child 3필드+`parent_* IS NULL` 3비트 마스크를 `CONCAT_WS('|', …)` 로 이어 SHA-256 한 **스토어드 생성컬럼**(BINARY(32))이라 의미는 복합키와 같고 인덱스는 48바이트로 끝난다. 접두 길이(`child_name(80)`)를 쓰지 않은 이유는 접두가 겹치는 서로 다른 패키지를 같은 키로 묶어 정상 엣지를 조용히 버리기 때문.
- `scan_id`/`container_id` 는 해시에 넣지 않고 키 앞에 그대로 둔다 — MySQL 은 생성컬럼의 기반 컬럼에 걸린 FK 에 `ON DELETE CASCADE` 를 못 쓴다. 감사 4컬럼 없음(`created_at` 만) — 스캔에 CASCADE 로 매달린 파생 기록이라 소프트삭제 대상이 아니고, 재스캔은 DELETE-then-INSERT 다.
- 근거: `20260806141456_package_dependency_graph.sql` + `20260809005223_pkgdep_edge_key_fix.sql`(옛 정의가 남은 공용 dev DB 를 같은 형태로 수렴시키는 보정).

## 2. CVE 도메인 — 검증된 피드에서 상속(스캔과 독립)

> 이 계열은 FK 를 걸지 않는다 — 피드마다 수집 순서가 독립이라 `cve_id` VARCHAR 자연키로 애플리케이션 조인한다(의도).

### tb_cve — CVE 마스터(NVD)
`cve_id [PRI]`, `summary`, `cvss`, `cvss_vector`, `cwe`, `epss`, `epss_percentile`, `published`
- `cve_id` 자연키 PK(명명규칙 예외 — CVE 번호 자체가 키라 대리키를 두지 않는다). 운영은 수십만 행(NVD 전체). CVSS·EPSS 의 **단일 진실 원천** — 화면은 여기서 라이브 조인해야 최신값을 본다.

### tb_kev_catalog — CISA KEV(악용 확인 목록)
`cve_id [PRI]`, `date_added`, `due_date`, `ransomware`, `note`
- KEV 등재 = 우선순위 상향. `due_date` 있으면 패치 기한 초과 판정.
- 테이블명·PK 모두 명명규칙 **예외**(FK-as-PK). `kev_catalog_id` 대리키를 새로 만들지 않는다.

### tb_cve_affected_package — CVE ↔ 영향 패키지
`cve_affected_package_id [PRI]`, `cve_id [MUL]`, `ecosystem`, `package_name [MUL]`, `fixed_version`
- **자연키 UNIQUE(cve_id, package_name, ecosystem)** — `ecosystem` 을 키에 넣어야 같은 패키지의 배포판별 조치버전이 안 덮어써진다(예: nginx 가 Rocky·Debian 각기 다른 fixed_version). upsert 는 ON DUPLICATE KEY.

### tb_package_summary — 영향 패키지 사전집계(packages.php 전용)
`package_name [PRI]`, `ecosystem [PRI]`, `cve_cnt`, `max_epss`, `fix_cnt`, `max_fixed`, `updated_at`
- `tb_cve_affected_package`(92만 행)를 매 로드마다 GROUP BY 하던 packages.php 를 위한 요약(8초→0.1초 미만). `cve_cnt`=COUNT(DISTINCT cve_id), `max_epss`=MAX(tb_cve.epss), `fix_cnt`=조치버전 있는 행 수.
- `max_fixed`: 조치버전의 자연순 최댓값. SQL `MAX()` 로는 못 구해(사전순이라 `...9` > `...11`) OSV 커넥터 실행 뒤 `vg_rebuild_package_summary()`(matcher.php)가 PHP 에서 계산해 채운다.
- OSV 커넥터가 돌 때만 `vg_rebuild_package_summary()` 가 트랜잭션으로 통째 재생성(읽는 쪽은 MVCC 로 옛 값을 보다 커밋 때 전환).
- 복합 자연키 PK 라 명명규칙 **예외** — 사전집계 테이블에 대리키를 만들지 않는다.

### tb_package_license_summary — 라이선스 위험도 사전집계(packages.php?tab=lang 전용)
`manager [PRI]`, `name [PRI]`, `license [PRI]`, `risk`, `pkg_count`, `updated_at`
- `tb_package_summary` 와 같은 패턴(사전집계로 화면 요청 시 재집계 회피). 대상은 언어 패키지
  8개 매니저(pip/npm/gem/composer/maven/nuget/cargo/go)뿐 — OS 패키지(rpm/dpkg/apk) 라이선스는
  이번 범위 밖(scope-out).
- `risk`: permissive/copyleft/unknown. `vg_license_classify()` 결과를 저장(재계산 없이 조회만).
- 갱신은 `vg_rebuild_license_summary()`(`src/license_summary.php`)가 **스케줄러 매 틱마다 무조건**
  DELETE 후 최신 스캔 기준으로 통째 재생성한다 — `tb_package_summary`(OSV 실행 시 갱신)와 달리
  OSV 게이트에 안 묶는다. 라이선스 데이터는 OSV 가 아니라 에이전트 ingest 로 들어오므로, OSV 게이트에
  묶으면 OSV 미등록/0건인 동안 KPI 가 영구히 0으로 보인다(PR#468 리뷰에서 발견·수정).
- 복합 자연키 PK 라 명명규칙 **예외**.

### tb_advisory — 국내 보안공지(KISA)
`advisory_id [PRI]`, `source`, `title`, `url [UNI]`, `published [MUL]`, `content`, `content_fetched_at`
- `url` 유니크. `content` 는 원문 본문. 관련 CVE 는 아래 정션에만 있다(옛 `cve_ids` CSV 는 드롭 — §정규화 참고).

### tb_advisory_cve — 공지 ↔ CVE 정션(1NF 정규화)
`advisory_cve_id [PRI]`, `advisory_id [FK CASCADE]`, `cve_id [MUL]`
- 공지↔CVE 의 **유일한 정본**. **UNIQUE(advisory_id, cve_id)** + `cve_id` 인덱스(CVE→공지 역조회). 읽기·쓰기 모두 여기서. 쓰기는 `vg_sync_advisory_cves` 가 멱등 동기화하고, 목록이 실제로 바뀌었는지를 bool 로 돌려준다(공지 upsert 의 '수정' 판정 근거).

## 3. 매칭 결과 — 우리 기여(런타임 상태·억제)

### tb_finding — 매처 판정(취약점) ★핵심
`finding_id [PRI]`, `scan_id [FK]`, `container_id`, `cve_id [MUL]`, `package_name`, `installed_version`,
`loaded`, `exposed`, `exposure_scope`, `runtime_status`, `in_kev`, `needs_restart`, `no_fix`,
`cvss`, `severity [MUL]`, `rationale`, `matched_at`
- 스캔×CVE×패키지 판정. `runtime_status` = EXTERNAL/LAN/FILTERED/LISTENING/RUNNING/LOADED/INSTALLED 7단계.
- **의도적 캐시(비정규화)**: `cvss`·`in_kev`·`severity` 는 `tb_cve`/`tb_kev_catalog` 값을 복제 보관한다. rematch 가 DELETE+INSERT 로 재계산하는 **머티리얼라이즈드 뷰**라 성능상 정당하다(3NF 위반 아님, 재계산 경로가 정합성 보장).
- `no_fix`: 벤더가 "아직 안 고쳤다"(조치 불가)고 확인한 건 표시(`tb_vendor_unfixed` 대조). 등급은 그대로 두되(런타임 노출 기준) "지금 고칠 수 있는 것"과 화면에서 분리 — 조치 불가가 덜 위험하다는 뜻이 아니라 지금 할 수 있는 일이 없다는 뜻.

### tb_finding_evidence — 판정 근거 구조화(1:1 확장)
`finding_id [PRI][FK CASCADE]`, `match_source [MUL]`, `fixed_version`, `source_package`, `source_version`,
`process_evidence`, `network_evidence`, `feed_updated_at`, `evidence_json`, `created_at`, `updated_at`
- `tb_finding` 의 **1:1 확장**. `tb_finding.rationale` 은 사람이 읽는 한 문장이라 기계로 되짚을 수 없어서, "왜 이 판정이 나왔는가"를 컬럼으로 쪼개 따로 담는다(외부 전달·재현·감사용).
- `match_source`: 이 판정을 만든 근거의 출처(기본 `catalog`) — 어느 피드 계열이 짚었는지 구분한다. `feed_updated_at` 은 그 근거를 준 피드의 갱신 시각이라 "얼마나 최신 지식으로 판정했나"를 남긴다.
- `source_package`/`source_version`: 매칭이 실제로 성립한 소스패키지 단위(백포트 판정의 핵심 축). `fixed_version` 은 그 시점 조치버전.
- `process_evidence`/`network_evidence`: 런타임 상태(로드·노출)를 뒷받침한 프로세스·소켓 근거. `evidence_json` 은 위로 안 떨어지는 나머지 원형.
- PK 는 `finding_id` — FK-as-PK 라 명명규칙 **예외**. 감사 4컬럼 없음(`created_at`/`updated_at` 만) — 부모 finding 이 rematch 로 DELETE+INSERT 되면 CASCADE 로 같이 지워지는 파생 캐시라 소프트삭제 대상이 아니다.

### tb_suppressed_finding — 억제된 건(설명가능한 오탐 억제)
`suppressed_finding_id [PRI]`, `scan_id [FK]`, `cve_id`, `package_name`, `installed_version`, `in_kev`, `cvss`,
`base_severity`, `suppress_reason`, `matched_at`
- 백포트 등으로 "이미 패치됨"이 증명돼 `tb_finding` 에서 뺀 건. 숨기지 않고 근거(`suppress_reason`)와 함께 호스트 상세에 표시.

### tb_remediation_note — 미조치 사유·승인자 메모
`remediation_note_id [PRI]`, `host_id [FK CASCADE]`, `cid`, `cve_id`, `package`, `reason`,
`approved_by`, `approved_at`, 감사 4컬럼
- 억제(`tb_suppressed_finding`)는 매처의 **자동 판정**이고, 이 표는 **사람이 남기는 메모**다. "이 취약점은 왜 지금 고치지 않는가"와 "그 판단을 누가 언제 했는가"만 붙든다 — 결재선·상태 전이·담당자·기한은 의도적으로 두지 않는다(본격 조치 워크플로는 `export.php` 로 넘겨받는 외부 시스템 몫).
- **UNIQUE(host_id, cve_id, package, cid)** 자연키. `tb_container.container_id`·`tb_finding.finding_id` 는 스캔마다 새로 발급되는 대리키라 스캔 간 비교가 안 되므로, 호스트 + 컨테이너 **이름**(`cid`, 호스트 자신은 `''`) + CVE + 패키지명으로만 묶는다. `''` 로 정규화하는 이유는 NULL 이 UNIQUE 에서 중복을 못 막기 때문.
- 철회는 소프트삭제라 같은 조합이 다시 저장될 수 있어야 한다 → 저장은 `ON DUPLICATE KEY UPDATE` 로 되살린다.
- `approved_by` 는 `tb_user.user_id` 지만 **FK 를 걸지 않는다**(감사 관련 테이블 관례 — 계정이 지워져도 판단 기록은 남아야 한다). 조회는 `src/remediation_note.php`, 외부 전달은 `export.php` 의 `remediation_*` 3필드.

### 억제 근거 4종(스캔에 매달림, 매처가 참조)
| 테이블 | PK | 컬럼 | 역할 |
|---|---|---|---|
| `tb_pkg_changelog_cve` | `pkg_changelog_cve_id` | `scan_id`, `package_name`, `cve_id`, `evidence` | ② changelog 에 그 CVE 수정 기록 |
| `tb_applied_errata` | `applied_errata_id` | `scan_id`, `package_name`, `cve_id`, `evidence` | ③ 벤더가 "이 빌드에서 고쳤다" 확인 |
| `tb_debsecan` | `debsecan_id` | `scan_id`, `cve_id`, `package_name` | ④ 데비안 트래커에 **없으면** 고쳐진 것(역방향) |
| `tb_stale_lib` | `stale_lib_id` | `scan_id`, `pid`, `comm`, `package_name`, `lib_path` | 억제 **취소** — 패치됐지만 옛 .so 물고 있음 → 재시작 필요 |

### 벤더별 판정 소스(배포판·커널의 중앙 OVAL/에라타 카탈로그)
데비안 계열은 `tb_debsecan`/`tb_applied_errata`(위 표)가 담당하고, 나머지 배포판·커널은 아래 테이블이 같은 역할(백포트로 인한 오탐 방지·조치 불가 판정)을 한다. 모두 스캔에 매달리지 않고 벤더 피드에서 독립적으로 채워지며, 매처가 참조한다.

#### tb_debian_tracker — 데비안 보안 트래커(중앙 수집)
`debian_tracker_id [PRI]`, `release_codename [MUL]`, `pkg_name [MUL]`, `is_binary`, `cve_id`,
`fixed_version`, `other_versions`, `urgency`, `has_fix`, 감사4컬럼
- **UNIQUE(release_codename, pkg_name, is_binary, cve_id)**. 데비안은 보안패치를 백포트하므로(버전을 안 올리고 고친다) 버전 비교만으로는 오탐이 대량으로 남는다(실측 raspberrypi5-00: HIGH 160 중 73건).
- `tb_debsecan`(위 표 ④)과 **같은 지식을 중앙이 직접 받는 쪽**이다. 예전엔 대상 서버에 debsecan 을 설치해 판정을 받아왔는데, 에이전트는 사실만 수집하고 판정 지식은 중앙이 갖는 게 맞고 폐쇄망 서버엔 apt 설치조차 못 한다. 그래서 debsecan 이 받아 쓰는 바로 그 데이터를 커넥터(`debtracker`)가 당겨온다.
- 판정 규칙은 debsecan 원본(`Vulnerability.is_vulnerable`)과 동일하다 — 바이너리 항목(`is_binary=1`)은 설치 바이너리 버전 < `fixed_version` 이면 취약, 소스 항목은 설치 소스 버전 < `fixed_version` 이면서 `other_versions` 에 없을 때 취약, `fixed_version` 이 비면 아직 수정본이 없다는 뜻이라 무조건 취약.
- 테이블명이 이미 불가산이라 단수화 없이 **PK 만** `debian_tracker_id` 로 바뀌었다.

#### tb_ubuntu_oval — 우분투 벤더 판정(Canonical OVAL)
`ubuntu_oval_id [PRI]`, `release_codename [MUL]`, `pkg_name`, `cve_id`, `fixed_evr`, `severity`, 감사4컬럼
- **UNIQUE(release_codename, pkg_name, cve_id)**. `fixed_evr` = NULL 이면 "아직 수정본 없음"(조치 불가) — Canonical OVAL 테스트에 state 가 없는 경우. 데비안/RHEL 계열과 달리 우분투는 이 하나로 조치버전·조치불가를 모두 표현.

#### tb_vendor_errata — RHEL 계열 벤더 권고(OVAL)
`vendor_errata_id [PRI]`, `vendor`, `release_major`, `pkg_name [MUL]`, `cve_id`, `fixed_evr`, `advisory`, `severity`, 감사4컬럼
- `vendor` = redhat/almalinux(Rocky 는 OSV 가 이미 조치버전을 주므로 제외 — 중복 수집 회피). **UNIQUE(vendor, release_major, pkg_name, cve_id, fixed_evr)** — 같은 (패키지,CVE)가 마이너 릴리스마다 다른 EVR 로 고쳐지므로(el9_2·el9_4…) EVR 까지 키에 넣어 전부 보관한다.

#### tb_vendor_unfixed — Red Hat 미수정 CVE(조치 불가)
`vendor_unfixed_id [PRI]`, `vendor`, `release_major`, `component [MUL]`, `cve_id`, `fix_state`, `severity`, `cvss`, `checked_at`, 감사4컬럼
- `tb_vendor_errata`(OVAL)엔 수정본이 나온 것만 있어, Red Hat 이 "영향받음/고치지 않겠다/조사중/지원종료" 로 표시한 CVE 는 별도로 담는다(실측 UBI8: Trivy 523건 중 514건이 이것). **UNIQUE(vendor, release_major, component, cve_id)**. `component` 는 소스 패키지 단위(bzip2) — 설치된 바이너리에 펼쳐 `tb_finding.no_fix` 로 표시.

#### tb_kernel_cve / tb_kernel_cve_fix — 커널 CVE(kernel.org CNA 판정)
- `tb_kernel_cve`: `cve_id [PRI]`, `introduced_version`, `mainline_fixed`, 감사(created/updated만)
- `tb_kernel_cve_fix`: `cve_id+stream [PRI]`, `fixed_version`
- 둘 다 PK 는 명명규칙 **예외**(FK-as-PK / 복합 자연키) — 테이블명만 단수화했다.
- 커널은 배포판 버전 체계 밖(예: `linux-image-6.18.34+rpt-rpi-2712`)이라 배포판 트래커/OVAL 로 판정이 안 된다. kernel.org CNA 가 "어느 stable 시리즈의 어느 버전에서 고쳤는가"를 발행 — 구동 커널의 업스트림 버전과 대조해 배포판 무관하게 판정. 억제 방향으로만 쓴다(배포판이 업스트림보다 먼저 백포트한 경우는 억제하지 않고 트래커/OVAL 에 맡김 — 보수적).

## 4. 설정 점검·변화 추적

### tb_cce_finding — 보안설정 점검(CCE)
`cce_finding_id [PRI]`, `scan_id [FK]`, `code`, `ssg_rule_id`, `title`, `result [MUL]`, `severity`, `evidence`, `rationale`, `checked_at`
- CVE 가 아니라 잘못된 **설정**(SSH root 로그인·패스워드 인증·UID 0·MAC·방화벽) 판정. `result` = PASS/FAIL/NA. 신규 수집 없이 기존 수집물 재활용.
- `ssg_rule_id`: 이 점검이 묶인 SCAP Security Guide 룰 ID(`tb_compliance_rule.rule_id`). 비어 있으면 아직 SSG 에 매핑되지 않은(=우리만의) 점검.

### tb_compliance_rule — 보안설정 룰 카탈로그(SCAP Security Guide)
`compliance_rule_id [PRI]`, `rule_id [UNI]`, `title`, `severity`, `rationale`, `refs_json`, `ssg_version`, 감사4컬럼
- **`rule_id` 는 PK 가 아니다** — SSG 가 발행하는 룰 문자열 ID(`xccdf_org.ssgproject...`)라 이름이 겹친다. 그래서 대리키 PK 를 규칙대로 `compliance_rule_id` 로 두어 충돌을 피한다.
- 점검 룰을 코드에 직접 써 넣던 것(MITRE CCE 는 갱신 끊김, KISA 가이드는 API 없음)을 대신해, 오픈소스 룰셋 SSG(ComplianceAsCode)를 카탈로그로 받는다. `refs_json`: `{"cis@rhel9":"5.2.11","nist":"AC-17(a)","stig":"..."}` 형태로 CIS/NIST 800-53/STIG/PCI-DSS 참조를 담는다.
- 판정 로직(OVAL)까지 중앙화하진 못한다 — OVAL 은 살아있는 파일시스템을 프로브하는데 중앙은 에이전트가 보낸 사실만 가진다. 그래서 판정 가능한 룰만 `tb_cce_finding.ssg_rule_id` 로 묶고, 나머지는 "수집 항목 없음(판정 불가)"로 드러낸다.

### tb_control_mapping — 통제 기준 다중 매핑
`control_mapping_id [PRI]`, `rule_code [MUL]`, `framework [MUL]`, `control_id`, `control_name`, 감사 4컬럼
- 한 CCE 점검 결과(`tb_cce_finding.code`)를 **U-코드·ISMS-P·N2SF 세 체계의 증적으로 함께** 보기 위한 매핑. 예전엔 이 지식이 `src/cce.php` 주석(U-XX)과 `compliance.php` 의 화면 문자열에 흩어져 있어 한 점검 결과를 다른 기준으로 볼 수 없었다.
- **UNIQUE(rule_code, framework, control_id)** — 한 룰이 같은 기준의 여러 통제에 걸릴 수 있다(예: `CCE-SSH-ROOT` 가 ISMS-P 2.5.5 와 2.6.6 양쪽). `framework` 3종: `KISA_U`(기반시설 U-코드) / `ISMS_P` / `N2SF`. 어휘 SSOT 는 `vg_control_frameworks()`(`src/control_mapping.php`).
- **매핑 행 자체가 마이그레이션 시드다**(`20260808105913_control_mapping.sql`). `INSERT … ON DUPLICATE KEY UPDATE` 로 멱등하고, 소프트삭제된 행은 시드 재적용 때 되살아난다(선언한 상태로 수렴).
- **근거 없으면 행을 만들지 않는다** — U-코드는 `cce.php` 주석에 명시된 항목만, ISMS-P·N2SF 는 컴플라이언스 감사 리포트(2026-08-07)가 명시한 매핑과 같은 성격의 룰로 확장한 것만. 그래서 `CCE-SSH-PWAUTH`·`CCE-SEC-MODULE` 등은 U-코드 행이 아예 없다.

### tb_control_guide / tb_cce_rule_guide — 통제 설명·점검 조치 가이드
- `tb_control_guide`: `control_guide_id [PRI]`, `framework`, `control_id`, `description`, 감사 4컬럼 — **UNIQUE(framework, control_id)**
- `tb_cce_rule_guide`: `cce_rule_guide_id [PRI]`, `rule_code [UNI]`, `summary`, `remediation`, 감사 4컬럼
- 통제 상세 화면(`/control.php`)이 읽는다. `tb_control_mapping` 은 "어느 룰이 어느 통제인가"만 갖고 있어서, 통제를 눌러도 결과 표만 보이고 **무엇을 요구하는 기준인지·어떻게 고치는지**를 담을 자리가 없었다.
- **테이블을 둘로 나눈 이유**: 설명은 통제 단위(같은 룰도 기준마다 요구가 다르다)이고 조치는 룰 단위(기준과 무관하게 같은 설정 파일을 고친다)다. 합치면 한 룰의 조치가 기준 수만큼 복제된다.
- **행 자체가 마이그레이션 시드다**(`20260809093626_control_guide.sql`, `INSERT … ON DUPLICATE KEY UPDATE` 로 멱등). 조치 문구는 `src/cce.php` 의 실제 판정 로직(보는 파일·지시어·임계값)에서만 끌어냈다 — 판정과 조치가 어긋나면 사용자는 고쳐도 FAIL 이 안 사라지는 안내를 따르게 된다.
- **근거가 모자라면 행을 만들지 않는다**(tb_control_mapping 과 같은 원칙). 가이드가 없는 통제·룰은 화면이 "설명 준비 중"으로 비워 둔다 — 빈 문자열 행으로 채우지 않는다.

### tb_compliance_snapshot / tb_compliance_snapshot_control — 컴플라이언스 판정 스냅샷
- `tb_compliance_snapshot`: `compliance_snapshot_id [PRI]`, `snapshot_date [UNI]`, `taken_at`, 감사 4컬럼
- `tb_compliance_snapshot_control`: `compliance_snapshot_control_id [PRI]`, `compliance_snapshot_id [FK CASCADE]`,
  `control_key`, `framework_ids`, `status_label`, `violation_count`, `unjudged_count`, `evidence(JSON)`, 감사 4컬럼
- `compliance.php` 는 그동안 "그때그때 판정만" 하고 저장이 없어서 "작년 심사 시점엔 어땠나"에 답할 수 없었다. 심사 증적의 본질은 시점이 아니라 **시계열**이라, 스케줄러(`bin/scheduler.php`)가 하루 1건씩 통제별 판정 결과를 남긴다.
- **UNIQUE(snapshot_date)** — 하루 1건. 같은 날 두 번 돌아도 UPSERT 로 덮어쓴다. 자식은 **UNIQUE(compliance_snapshot_id, control_key)**.
- `control_key` 3종(`patch`/`asset`/`secops`)과 `framework_ids` 는 `VG_COMPLIANCE_CONTROLS`(`src/compliance.php`)에서 온다. **키는 DB 에 그대로 저장되므로 바꾸면 과거 스냅샷과 이어지지 않는다 — 추가만 한다.**
- `status_label` 4종(준수 / 판정 불가 / 부분준수 / 미준수)의 SSOT 는 `vg_compliance_status()`. 화면과 스케줄러가 같은 함수를 쓴다 — 판정 로직이 두 벌이면 화면과 증적이 서로 다른 답을 낸다.
- `unjudged_count` 는 **판정 불가** 건수다. 위반 건수만 저장하면 "근거가 모자라 판정을 못 했다"는 사실이 증적에서 사라지고 나중에 그 스냅샷을 "위반 0건 = 준수"로 되읽게 된다(허위 안심).
- `evidence` JSON 은 `{total, truncated, items[], unjudged{…}}`. 상한은 `VG_COMPLIANCE_EVIDENCE_MAX`=500 이고 넘으면 `truncated=true` 로 **잘렸다는 사실 자체를 증적에 남긴다** — 무제한 JSON 은 위반이 수천 건인 환경에서 스냅샷 행이 본 데이터보다 커진다.

### tb_pkg_change — 패키지 변화 이력(시계열)
`pkg_change_id [PRI]`, `host_id [FK]`, `scan_id [FK]`, `manager`, `package_name`, `change_type`, `old_version`, `new_version`
- 최근 2개 스캔 대조로 설치/제거/업그레이드/다운그레이드 기록. 차별점 ④(변화 추적).

## 6. 인증·권한·감사

### tb_user — 로그인 계정
`user_id [PRI]`, `username [UNI]`, `password_hash`, `session_token`, `role`, `failed_login_count`, `locked_until`,
`created_at`, `last_login`
- 역할 3단계: admin/operator/user. `password_hash` = password_hash(). admin 은 코드에서 항상 전체 허용(잠금 방지).
- `session_token`: 계정당 활성 세션 1개. 로그인 성공 때 새로 발급해 DB·세션에 함께 저장하므로, **이 컬럼을 덮어쓰는 것 자체가 기존 세션 무효화**다(다른 곳에서 로그인하면 앞의 세션이 끊긴다). 로그아웃·세션 만료 때 NULL 로 정리한다.
- `failed_login_count`/`locked_until`: 연속 로그인 실패 잠금(`LOGIN_MAX_FAILS`·`LOGIN_LOCK_MINUTES` — `docs/ui-configuration.md`). 로그인 성공 시 둘 다 초기화된다.
- 세션 유휴·절대 만료는 DB 가 아니라 코드 상수다(`VG_SESSION_IDLE_SECONDS`=1800, `VG_SESSION_ABSOLUTE_SECONDS`=43200 — `src/auth.php`). 만료되면 `session_expire` 감사로그를 남기고 `session_token` 을 지운다.

### tb_role_permission — 역할×메뉴 권한(설정형 RBAC)
`role_permission_id [PRI]`, `role [MUL]`, `menu_code`, `allowed`
- 역할별 메뉴 접근을 화면에서 설정. 가드는 `vg_require_menu()`.

### tb_api_token — Export API 읽기 토큰
`api_token_id [PRI]`, `label`, `token_hash [UNI]`, `token_prefix`, `expires_at`, `last_used_at`, `created_by`
- `GET /export.php` 전용. **SHA-256 해시만 저장**(원문 1회 표시). `token_prefix` 는 목록 식별용.
- `expires_at`: **NULL = 무기한**(기존 발급분은 그대로 계속 쓰인다 — 하위호환). 값이 있고 지났으면 `vg_api_token_verify()` 가 인증 실패로 처리하고 `api_token_expired` 감사로그를 남긴다. 발급 선택지(무기한/30일/90일/1년)와 만료 임박 기준(7일)은 `src/tokenexpiry.php` 가 두 토큰에 공통으로 소유한다. 자동 갱신·재발급은 없다.

### tb_agent_token — 에이전트 수집 토큰(호스트 바인딩)
`agent_token_id [PRI]`, `host_fqdn [MUL]`, `label`, `token_hash [UNI]`, `token_prefix`, `expires_at`, `last_seen_at`, `is_revoked [MUL]`, `created_by`
- 각 토큰이 발급 시 정한 `host_fqdn` 만 갱신 가능 — 침해된 대상 1대가 남의 호스트를 위조하는 걸 ingest.php 가 막는다. 해시만 저장, `is_revoked` 즉시 폐기, 활성은 호스트당 1개.
- `expires_at` 은 `tb_api_token` 과 같은 규칙(NULL=무기한). 만료된 토큰은 `agent_token_expired` 감사로그와 함께 거부된다. 대응 기준: ISMS-P 2.5.1 · N2SF AC-1(4).

### tb_agent_replay_nonce — 에이전트 재전송(재생) 공격 방지
`agent_token_id [PRI][FK CASCADE]`, `nonce_hash [PRI]`, `expires_at [MUL]`
- 토큰이 유효해도 **가로챈 요청을 그대로 다시 보내면** 통과한다. 그걸 막으려고 요청마다 1회용 nonce 를 받아 여기 소진 기록을 남긴다 — 이미 있는 nonce 면 거절.
- PK 가 `(agent_token_id, nonce_hash)` 복합 자연키라 명명규칙 **예외**. 삽입 자체가 중복 검사라 별도 조회가 필요 없다.
- `expires_at` 인덱스는 만료분 정리(reap)용 — 안 지우면 무한히 쌓인다. `nonce_hash` 는 원문이 아니라 해시(CHAR(64))만 담는다.
- 감사 4컬럼 없음. 토큰이 폐기되면 CASCADE 로 같이 사라지는 휘발성 운영 데이터다.

### tb_activity_log — 행위 감사 로그
`activity_log_id [PRI]`, `user_id [MUL]`, `user_name`, `actor_type`, `scope [MUL]`, `scope_id`,
`activity_type [MUL]`, `message`, `subject`, `action [MUL]`, `data`, `ip_address`
- 로그인·커넥터 저장/삭제/실행·사용자 추가/삭제·ingest 수신 등 기록. `vg_log_activity()`. 조회는 `activity.php`.
- **접속기록 5요소**(ISMS-P 2.9.4): 식별자(`user_id`/`user_name`) · 접속일시(`created_at`) · 접속지 IP(`ip_address`) · 처리한 정보주체(`subject`) · 수행업무(`action`). 앞 셋은 원래 독립 컬럼이었고, 뒤 둘만 `20260808105747_activity_log_5elements.sql` 이 추가했다(일부가 `data` JSON 안에 묻혀 있어 정렬·조회가 안 됐다).
- `subject` — 이 제품은 **개인정보를 처리하지 않는다.** 그래서 ISMS-P 가 말하는 "처리한 정보주체" 자리에 실제로 담는 값은 그 행위가 다룬 **대상 자원**(호스트 FQDN·CVE ID·패키지명·계정 아이디 등)이고, 컬럼 주석에도 그렇게 적혀 있다.
- `action` — 수행업무 정규화 동사(`READ`/`CREATE`/`UPDATE`/`DELETE`/`EXPORT`/`LOGIN`/`EXECUTE`/`OTHER`). 기존 `activity_type`(세부 이벤트 코드) **위의 정규화 계층**이며 어휘는 `vg_activity_action()` 이 소유한다.
- 인덱스는 `action` 에만 걸었다 — 조회 화면의 '수행업무' 필터가 등호로 거는 유일한 새 컬럼이다. `subject` 는 부분일치(`LIKE '%…%'`) 검색이라 인덱스가 안 먹어서 만들지 않는다.
- 테이블명은 이미 단수(불가산)라 그대로, PK 만 `activity_log_id` 로 바꿨다.

### tb_activity_review — 접속기록 점검 이력(월 1회)
`activity_review_id [PRI]`, `period_start [MUL]`, `period_end`, `reviewed_by`, `reviewer_name`, `reviewed_at`,
`result`, `note`, 감사 4컬럼
- ISMS-P 2.9.5(로그 및 접속기록 점검) — 접속기록을 **월 1회 점검했다는 사실**을 남긴다. 점검 대상 기간·수행자·결과가 한 행.
- **UNIQUE(period_start, period_end)** — 같은 기간을 두 번 기록하지 못하게 막는다. 월 1회면 그 달 1일~말일.
- `result` 3종: `OK`(이상없음) / `FINDING`(이상징후) / `NA`(대상없음).
- `reviewed_by` 는 `tb_user.user_id` 지만 **FK 를 걸지 않는다**(감사 관련 테이블 관례). 계정이 지워져도 점검 이력은 남아야 하므로 수행자 아이디를 `reviewer_name` 에 스냅샷으로 함께 박는다.

## 7. 인프라

### tb_setting — 전역 운영 설정
`setting_id [PRI]`, `setting_key [UNI]`, `setting_value`, `value_type`, `description`, 감사 4컬럼
- 조직마다 달라지는 판정 기준값을 코드에서 뺀 곳(CLAUDE.md 보안·운영 준수 원칙 1 "하드코딩 금지"). SLA 기준일은 업계 관행값이 아니라 **조직 내부 규정**이라 코드를 고쳐야 바꿀 수 있으면 제품으로 쓸 수 없다.
- **전역 값 하나씩만 둔다**(YAGNI) — 조직별·호스트별 다단계 설정은 만들지 않는다. `value_type` 은 `int`/`string`.
- **코드의 상수는 지우지 않고 "설정 행이 없을 때의 폴백"으로 남는다** — 마이그레이션이 아직 안 든 DB 에서도 지금과 똑같이 동작해야 하기 때문. 읽기는 `vg_setting_int()`/`vg_setting()`(`src/setting.php`, 요청당 1회 전체 로드 후 정적 캐시), 쓰기는 `settings.php`(관리자 전용) 만.
- 시드 5키(기본값·폴백 상수는 `src/compliance.php`): `compliance.sla_kev_days`(15) · `compliance.sla_crit_days`(30) · `compliance.sla_high_days`(60) · `compliance.partial_max`(5) · `compliance.history_lookback_margin_days`(14). 항목 정의(라벨·min/max)의 SSOT 는 `vg_setting_defs()` 이고 **기본값은 거기 두지 않는다** — 같은 숫자를 두 곳에 두면 갈라진다.
- 시드는 재실행 시 `setting_value` 를 **덮어쓰지 않는다**(관리자가 화면에서 바꾼 값이 기본값으로 되돌아가면 안 된다). 설명문만 최신으로 맞춘다.
- 현재 설정 키 목록의 사람용 정본은 `docs/ui-configuration.md`.

### tb_schema_migrations — 적용된 마이그레이션
`filename [PRI]`, `applied_at`
- `deploy/migrate.sh` 가 `db/migrations/*.sql` 중 미적용분만 사전순 적용하고 여기 기록. 감사컬럼 없음(운영 메타).
- **명명규칙 예외 — 테이블명도 PK 도 건드리지 않는다.** 러너가 자기 이력을 이 이름으로 찾기 때문에, 바꾸면 이력을 잃고 전체 마이그레이션이 재실행된다.

## 정규화 현황 (요약)

스키마는 **대체로 3NF**다. "다 쪼갰나?"에 대한 정직한 답:

**정규화한 것**
- `tb_cve_affected_package`: 자연키 UNIQUE(cve_id, package_name, **ecosystem**) — 배포판별 조치버전이 서로 덮어쓰던 2NF 버그 수정.
- `tb_advisory_cve`: `tb_advisory.cve_ids` CSV → 정션(1NF). CVE 역조회·인덱스 검색 가능. **contract 완료** — CSV 컬럼은 드롭했고(`20260809151827_advisory_drop_cve_ids.sql`), 정션이 유일한 정본이다(이슈 #520).
- 인덱스 보강: `tb_finding.cve_id` 등 라이브 조인 경로.

**의도적 비정규화(위반 아님 — 그대로 둔다)**
- `tb_finding` 의 cvss/severity/in_kev: rematch 가 재계산하는 **캐시(머티리얼라이즈드 뷰)**. 성능상 정당, 정합성은 재계산 경로가 보장.
- `tb_scan` 의 os/kernel 등: 수집 **시점 스냅샷**(현재값 복제가 아니라 시점 사실).
- `tb_exposure`/`tb_process` 의 `loaded_pkgs` CSV: **원본 수집 신호** — 쪼개도 이득 없어 그대로.

**FK 정책**
- 스캔 소유 계열(scan_id·host_id·feed_connector_id·advisory_id)엔 FK. CVE 도메인(cve_id 자연키)엔 FK 를 안 건다 — 피드별 수집 순서 독립성을 위해 애플리케이션 조인(의도적 설계).
- **사람 참조는 두 갈래다.** 감사·판단 기록 계열(`tb_remediation_note.approved_by`·`tb_activity_review.reviewed_by`)은 사용자 FK 를 걸지 않는다 — 계정이 지워져도 "누가 그렇게 판단했다"는 기록은 남아야 한다(수행자 아이디를 스냅샷 컬럼에 함께 박는다). 반면 `tb_host.approved_by` 는 FK 를 걸되 `ON DELETE SET NULL` 이라 이력만 끊고 등급은 남는다.
- `tb_package_dependency` 의 유일성은 생성컬럼 `edge_hash` 로 건다. **생성컬럼의 기반 컬럼에 걸린 FK 는 `ON DELETE CASCADE` 를 쓸 수 없어서**(MySQL 제약) `scan_id` 는 해시에 넣지 않고 유니크 키 앞에 그대로 둔다.
- FK 이름은 부모 PK 이름과 같다(명명규칙 3). 그래서 `ON h.host_id = s.host_id` 처럼 조인 양쪽이 같은 이름으로 읽힌다.
