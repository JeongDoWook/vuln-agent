# changelog 억제층은 왜 한 건도 억제하지 않았나 — 운영 실측

> 기록 성격: **2026-07-28 시점의 운영 실측 자료**이고, 여기서 나온 권고는 이미 적용됐다
> (서드파티 가드에서 changelog 억제를 분리 · `VG_MATCH_FP_VERSION` 2). 현행 구조 설명은
> [`architecture.md`](architecture.md), 최신 수치는 웹 화면을 기준으로 한다.
> 원본 조사는 운영 DB **읽기 전용 조회**였고, 이 문서는 판정 코드를 바꾸지 않은 조사 결과다.

운영 억제 144만 건 중 **②changelog 를 근거로 억제된 건이 0건**이었다. 왜 그런지를 코드 경로와
벤더 1차 소스 대조로 확인한 기록이다.

## 결론

**changelog 신호는 맞았는데 그 앞의 게이트에 막혀 도달하지 못했다.** 억제 겹의 "순서" 때문이
아니라 `canSuppress` 가드(서드파티·재시작 필요) 때문이고, 걷어야 할 것은 **서드파티 가드에 걸린
4,088건뿐**이었다.

| 대상 | 건수 | 무엇이 막았나 | 벤더 대조 | 막은 게 옳은가 |
|---|---|---|---|---|
| 컨테이너 | 5,774 | `hostEvidenceOk`(changelog 는 호스트 수집물) | 전수 5,404건 **정탐**, 오탐 0 | **옳다** — 억제했으면 미탐 |
| 호스트·재시작 필요 | 168 | `staleEv` → `canSuppress=false` | 오탐 118 / 정탐 0 (단 옛 `.so` 사용 중) | **옳다** — 벤더가 고쳐도 지금 도는 코드는 취약 |
| 호스트·서드파티 | 4,088 | `!isDistroPkg` → `canSuppress=false` | 전수 **오탐 4,086 / 정탐 0** | **틀렸다** ← 유일한 개선 지점 |

그리고 **버전 비교가 이미 대부분을 커버한다** — changelog 근거가 붙은 건 중 억제된 21,956건은
사유가 전부 다른 층이었다(버전 비교 20,676 · 데비안 트래커 1,196 · 우분투 OVAL 84 · changelog 0).
changelog 가 억제할 수 있었을 것의 94%는 어차피 버전 비교가 먼저 잡는다.

## 코드 경로 — changelog 검사는 언제 도달하나

판정은 `server/src/matcher.php` 의 `vg_match_decide_cve()` 하나가 하고, **순서가 곧 우선순위**다
(먼저 걸리는 조건이 이기고 뒤는 평가되지 않는다).

```
1. 실행 중이 아닌 커널 → 억제      2. 커널 CNA(업스트림) → 억제
── 여기서 canSuppress 를 정한다: staleEv(재시작) · kernelPending(재부팅) · !isDistroPkg(서드파티) ──
3. 버전 비교(설치 ≥ 조치) → 억제   4. 배포판 트래커 / 우분투 OVAL → 억제
5. 중앙 벤더권고(OVAL, RHEL) → 억제 6. errata(dnf updateinfo) → 억제
7. changelog(백포트) → 억제  ← 마지막
```

> **문서와 코드의 번호가 다르다.** `CONTEXT.md`·`architecture.md` 는 억제를 "①OSV 버전필터
> ②changelog ③errata ④debsecan" 4겹으로 소개하지만 실제 코드에서 changelog 는 **일곱 번째**다.
> "②" 라는 이름 때문에 앞쪽 층으로 오해하기 쉽다.

7번 조건은 `$canSuppress && $ctx['hostEvidenceOk'] && $bpEv !== null` 이고 `hostEvidenceOk` 는
`($ctr === null) && $isDistroPkg` 다. 즉 changelog 가 억제하려면 **다섯 가지가 동시에** 성립해야
한다: ①호스트 패키지 ②배포판 저장소 패키지 ③재시작·재부팅 대기 아님 ④버전 비교로 안 걸림
⑤트래커/OVAL 도 "아직 취약"이라 말함.

②와 ⑤가 서로를 잡아먹는다. 배포판 패키지면 트래커·OVAL 이 그 릴리스를 관할하므로 ④·⑤가 먼저
판정하고, 트래커가 "아직 취약"인데 changelog 만 "고쳤다"고 하는 정면 충돌에서만 7번이 살아난다.
**운영에서 그 조합은 0건이다.**

**패키지 화이트리스트는 원인이 아니다.** `CONTEXT.md` 가 말하는 "핵심 13개 패키지 하드코딩"은
에이전트 수집 단계에 있고(rpm/dpkg 각각 13종), 살아남은 건의 상위 패키지(`openssl`·`curl`·
`libexpat1`·`systemd`·`libnss3`·`zlib1g`·`sudo`·`openssh-server`)는 전부 그 목록 안에 있다.
매처는 `p.name` 이 안 맞으면 `p.source_pkg` 로도 조회하므로 `libssl3t64` 같은 파생 바이너리도
`openssl` 기록에 걸린다.

## changelog 근거가 붙은 finding 의 운명

매처가 실제로 쓰는 키(`p.name` 또는 `p.source_pkg`)로 조인하면 10,030건이고, 전부 분해된다:

```
10,030 = 컨테이너 5,774 + 호스트 4,256
호스트 4,256 = 서드파티 저장소 4,088 + 재시작 필요 168 + 그 외 0
```

**"그 외"가 0건**이라는 게 핵심이다 — changelog 검사까지 내려온 finding 이 한 건도 없다.
서드파티 4,088건의 origin 은 `Raspberry Pi Foundation` 4,020 · `LOCAL`(수동 `.deb`) 68 이고,
앞엣것은 라즈베리 6대 × openssl 계열 세 바이너리라 **사실상 openssl 하나**다. 앞선 조사가
"changelog ↔ debsecan 충돌 16건"으로 본 것도 전부 같은 origin 이었다 — 충돌이라서가 아니라
서드파티라서 안 걸렸다.

## 벤더 1차 소스 전수 대조

버전 비교는 눈대중하지 않고 `vg_ver_cmp($installed, $fixed, 'dpkg')`(`server/src/vercmp.php`)를
그대로 호출했다. 데비안은 트래커 전체 JSON(80MB), 우분투는 `ubuntu.com/security/cves/<CVE>.json`
을 1차 소스로 썼다. `resolved`/`released` + 설치 ≥ 조치 = 오탐, `open`/`needed`/`deferred` = 정탐.

**호스트건 4,256건 전부**를 대조했다.

| 대상(막은 게이트) | 건수 | 오탐 | 정탐 | 판단불가 |
|---|---|---|---|---|
| 데비안 · 서드파티 | 4,068 | **4,068** | 0 | 0 |
| 데비안 · 재시작 필요 | 24 | **24** | 0 | 0 |
| 우분투 · 서드파티 | 20 | **18** | 0 | 2 |
| 우분투 · 재시작 필요 | 144 | **94** | 0 | 50 |
| **합계(1차 소스만)** | **4,256** | **4,204** | **0** | **52** |
| 합계(+ 중앙 수집 OVAL 보조) | 4,256 | 4,248 | 0 | 8 |

우분투 CVE 46종 중 38종만 1차 소스로 닿았다(`ubuntu.com` 이 재시도 4회에도 503/504). 나머지는
우리 파이프라인이 수집한 Canonical OVAL 로 채웠고 **보조**로 구분해 적는다 — 둘 다 있는 건에서
판정이 어긋나지 않았다. **어느 쪽으로 세든 정탐이 0건이다.**

**컨테이너건은 판정이 정반대다.** 같은 방법으로 전수 대조하면 데비안 2,673 · 우분투 2,731 =
**5,404건이 전부 정탐**(오탐 0)이다. 호스트에서 긁은 changelog 를 컨테이너에 적용했다면 그만큼을
잘못 숨겼을 것이다 — 호스트 `openssl` 이 패치됐다는 기록은 그 안에서 도는 `debian:12` 컨테이너의
`openssl` 과 무관하다. `hostEvidenceOk` 가드가 정확히 이 사고를 막고 있었다. (알파인 436건은
changelog 수집이 rpm/dpkg 에서만 돌아 판정 대상 자체가 아니다.)

## 권고 — 이 조사의 PR 에서 적용했다

**changelog 억제를 서드파티 가드에서 뺀다. `staleEv`(재시작)·`kernelPending`(재부팅) 가드와
컨테이너 제외는 그대로 둔다.** 구현은 억제 보류를 성격이 다른 둘로 나눈 것이다 — 근거 종류를
가리지 않는 **런타임 보류**와 버전 비교 계열에만 해당하는 **서드파티 보류**. changelog 는 앞엣것만
본다. 판정이 바뀌었으므로 `VG_MATCH_FP_VERSION` 을 2 로 올렸다(안 올리면 입력이 같은 스캔의 지문이
같아 새 결과가 저장되지 않는다). 계약은 `tests/matcher_suppress_test.php` 로 고정했다(스모크 편입).

근거: 서드파티 가드의 사유는 *"배포판 조치안과 버전 체계가 달라 자동 판정 불가"* 인데 이건 **EVR
비교에만** 해당한다. changelog 는 버전을 비교하지 않고 그 빌드 자신의 변경 기록에 CVE 번호가
박혀 있는지만 보므로, 오히려 벤더 데이터가 닿지 않는 서드파티 빌드에서 **유일하게 신뢰할 수 있는
근거**다. (라즈베리 저장소를 데비안 파생으로 인정하는 쪽이 더 근본적일 수 있으나, 그건 그
저장소가 **항상** 데비안 EVR 체계를 따른다는 가정이 필요하다. changelog 경로가 더 좁고 안전하다.)

**미탐 위험도 확인했다** — 걷히는 4,088건 중 `no_fix` 0건, CISA KEV 등재 0건이다. "지금 조치할 수
없는 것"이나 "실제로 악용 중인 것"을 화면에서 지우지 않는다.

**효과.** 화면에 실제 뜨는 것(호스트별 최신 스캔) 기준으로 finding 총계는 34,947 → 34,587
(−360, −1.0%)이고 그중 HIGH −120 · LOW −240 이다. 전체 대비 1%는 작아 보이지만 **라즈베리 6대의
HIGH 는 70건 중 20건(28.6%)이 이미 패치된 것**이었다 — 사람이 대응 우선순위를 보는 화면이 HIGH
라는 점에서 이 비율이 실제 비용에 가깝다. 한편 4,088건의 고유 (패키지, CVE) 종류는 73개, 고유
CVE 는 31개다. 같은 오탐이 스캔 162개 × 바이너리 3개로 부풀려진 것이라 "취약점 4천 개가
사라진다"로 읽으면 안 된다.

**수집을 끄는 안은 권하지 않는다.** [리소스 프로파일](에이전트-리소스-프로파일.md) 실측이
`full` 3.7s / `--no-changelog` 3.5s, 피크 RSS 는 양쪽 다 61.6MB 다. 대상이 13개 패키지로 고정된
상수 비용이라 0.2초를 아끼려고 서드파티 빌드의 유일한 백포트 근거를 버릴 이유가 없다.

## 한계

- **조인이 실제 판정을 재현한 게 아니다.** 매처를 다시 돌린 게 아니라 SQL 조인으로 "근거가
  있었는데 finding 으로 남은 것"을 센 것이라, 조인 키에 따라 수가 크게 흔들린다(`scan+cve`
  12,366 · `scan+pkg+cve` 3,005 · 매처와 같은 `name 또는 source_pkg` 10,030). 마지막을 정본으로 삼았다.
- **`tb_pkg_changelog_cve` 에 `container_id` 가 없어**(호스트에서만 수집) 기록 하나가 같은 스캔의
  컨테이너 finding 에도 조인된다 — 위 5,774건이 그것이고 매처는 애초에 억제 대상으로 보지 않는다.
- **같은 취약점이 여러 번 세어진다** — 호스트 4,256건은 스캔 162개에 걸쳐 있고, `openssl` 하나가
  세 바이너리로 갈린다. 화면에 뜨는 행 수이지 취약점 종류 수가 아니다.
- **우분투 1차 소스가 불안정하다**(503/504). 대조 못 한 건은 오탐으로 추정하지 않고 판단불가로
  남겼다 — 결론의 무게는 전량 1차 소스로 확인한 데비안 4,092건이 지고 있다.
- **운영 DB 가 살아 있어** 같은 쿼리의 총계가 조회 시점마다 몇 건씩 달랐다. 수치는 스냅샷이다.
- **`정탐` 판정은 벤더 데이터의 최신성에 의존한다.** 다만 이번 결론(서드파티 4,088건 오탐)은
  반대 방향이라 이 편향의 영향을 받지 않는다.
